# "사내 통합 MCP"라고 하려면 무엇을 더해야 할까 — 회의 (2026-11-02)

- 참석: 리드(진행), 시장·경쟁 조사(웹), 아키텍트(코드 진단), 고객사 정보보안팀장 겸 IT 관리자(가상, 직원 300명·ISMS-P 대상), 제품·UX 기획. 모두 에이전트예요. 코드는 고치지 않았어요.
- 기준: `CLAUDE.md`, `docs/ADR.md`(ADR-01·03·05·10·13·14·15·18·19·20·21·23·25·26), `docs/차별화회의_2026-10-31.md`, `docs/넓힐후보회의_2026-10-31.md`, `docs/남은작업_2026-11-01.md`, `docs/MCP_UX_TEST.md`, MCP 코드(`core/tool-registry.ts`, `modules/mcp/`), 공식 제품 문서(아래 출처, 2026-11-02 확인).
- 하이웍스·다우오피스·플로우 비교는 10/31 회의에 있어서 다시 보지 않았어요.

## 한눈에

1. **지금은 "안전한 MCP 하나"이지 "사내 통합 MCP"가 아니에요(4명 모두).** 도구가 둘(빈 회의실 후보·공지 제목)이고, 앱 안에 있는 담당 찾기·문의·휴가·IT FAQ·첫 2주 할 일·탕비실이 MCP에는 하나도 없어요. 시장에서 "통합"이라 부르는 제품은 여러 시스템을 한 입구로 묶고, 관리자가 도구·앱·사용자 단위로 보고 끌 수 있어요.
2. **쓰기 도구를 늘리는 쪽으로 가지 않아요.** 경쟁 제품은 쓰기가 40% 안팎(Atlassian 약 250개 중 40%, Notion 70개 중 31개, Google 65개 중 26개)이고 사람 확인 단계는 거의 없어요. 고객 보안팀은 "MCP에 쓰기 도구를 주면 승인 안 한다"고 했어요. 우리 길은 **읽기 도구와 "앱 확인 링크" 동작을 늘리는 것**이에요. 쓰기는 늘 앱에서 사람이 한 번 눌러요(ADR-03).
3. **차별점은 넷이에요. 시장에서 아무도 잘 안 해요.**
   - **A. 실행은 앱에서 한 번(확인 링크)을 도구 계약으로 공개.** Glean만 블로그에 "영향 큰 쓰기는 기본 확인"이라고 적었고, 나머지는 바로 써요.
   - **B. 출력 칸 화이트리스트·이름 비노출.** 경쟁 제품은 "사용자가 볼 수 있으면 다 줘요". 칸을 잘라 내는 건 게이트웨이 DLP 말고는 없어요(OWASP MCP Top 10의 과다 공유).
   - **C. "이 일은 어느 팀에 물어요?" 도구.** 사람·조직 찾기는 있지만, 업무 분장표 근거로 받을 팀을 답하고 문의 준비까지 잇는 MCP는 없어요(10/31 축 A, UX 시험에서 가장 크게 실패한 질문 U5).
   - **D. 국내 그룹웨어 옆에 붙는 회사별 한 벌.** 국내는 플로우 말고 공식 MCP가 확인되지 않았고, 국내 리전·구축형 엔터프라이즈 MCP도 확인되지 않았어요(ADR-23과 맞아요).
4. **차별을 말하기 전에 기반이 먼저예요.** 보안팀은 지금 상태로는 승인하지 않아요: MCP 접근이 접속기록(1년)에서 빠져 있고, 허용 앱을 등록·승인할 화면이 없고(SQL로 넣어요), 앱 확인 링크가 봉인되지 않았어요(B11). 직원 쪽에서는 연결 자체가 막혀요(U1~U3).
5. **"통합"은 한 회사 안의 여러 시스템을 묶는 뜻이에요.** 회사마다 한 벌이라(ADR-23) 여러 회사를 묶는 MCP는 만들지 않아요.

## 2. 지금 코드가 하는 것과 못 하는 것(아키텍트)

하는 것:
- 쓰기 도구는 타입 수준에서 막혀요(`ToolDef.access: 'read'`, `core/tool-registry.ts`).
- 인가: 미리 등록한 기밀 클라이언트만, PKCE S256·`resource` 필수, 토큰 AES-GCM 봉인, 요청마다 iss·aud·만료·허용 클라이언트 검사, 갱신 때 재직 재확인(`modules/mcp/auth-service.ts`, `tokens.ts`).
- 실제 자료는 `securityApproved` 클라이언트에만, 출력은 zod `.strict()` 화이트리스트(`mcp-route.ts`, `tools.ts`).

못 하는 것:
- **도구 하나 더하기가 비싸요.** 레지스트리·입력 스키마·등록 분기·범위·횟수 제한·웹 라벨 등 일곱 곳을 고쳐요.
- **도구별 운영 스위치가 없어요.** "모두 모의인가"도 어댑터 전체로 한 번에 봐요.
- **"내 것" 조회를 못 해요.** 접근 토큰에 가명 ID·클라이언트·범위만 있고 부서·역할·idpSubject가 없어요.
- **MCP 호출이 접속기록에 없어요.** `ACCESS_ACTIONS`(`core/access-record.ts:10`)에 MCP가 없어서 감사 로그(7일)에만 남아요.
- **앱 확인 링크는 서명만 있고 봉인이 없어요.** 풀면 가명 ID·방·시각이 보여요(`core/proposal-token.ts`, B11·REVIEW L3).
- **직원 × 앱마다 승인이 하나**라 두 번째 기기를 연결하면 첫 연결이 끊겨요(U6). CLI는 연결할 수 없어요(DCR·CIMD·루프백 없음, U1~U3).
- resources·prompts·elicitation은 쓰지 않아요.

편의에서 지지 않는 법:
- **탭 한 번 약속.** 링크가 확인 시트를 바로 열고(지금 회의실은 카드 → 버튼 → 시트로 두 번), 시트의 [보내기]·[예약하기]가 유일한 확인이에요. 링크를 연 건 확인이 아니에요.
- **상태 도구로 대화를 닫기.** 확정 뒤 "AI 앱에서 '됐어?'라고 물어보세요" → `my_requests_status`가 답해요. 바로 실행하는 쪽과 체감이 거의 같아요.
- **안전을 결과 문장으로.** 도구 결과에 "확정은 앱에서 한 번 · 링크는 본인만 · 10분 유효"를 늘 넣어요. 동의 시트도 "읽기와 준비만 해요. 보내기·예약은 앱에서 직접 눌러요"로 바꿔요.
- **안 하는 것:** MCP elicitation처럼 확인을 AI 앱 안에서 받는 방식. 확인이 우리 손을 떠나요(ADR-14에서 버린 대안).

**11/2 진행:** 넷 다 했어요.
- B11: 제안 토큰을 `core/seal.ts`로 봉인했어요. 링크를 풀어도 가명 ID·방·시각이 보이지 않아요. 길이는 그대로예요(약 460자). 더 줄이려면 서버에 두는 짧은 ID가 필요해서 "제안 토큰은 DB에 쓰지 않아요" 선과 같이 따로 정해요(U7).
- 접속기록: `mcp.connect`(동의 시트 허락)·`mcp.call`(도구를 부른 요청마다, 거부 포함)·`mcp.disconnect`(S6 끊기)를 1년 남겨요. 도구 이름·입력·클라이언트는 넣지 않아요(도구·클라이언트는 감사 로그 7일).
- 도구 정의: 선언은 `core/tool-registry.ts`의 `mcp` 칸(범위·제목·뺀 칸), 구현은 `modules/mcp/tool-impls.ts` 한 표예요. `/mcp`는 도구 이름으로 나누지 않아요. 횟수 제한 키는 `mcp.<도구>`로 저절로 정해져요. 도구별 운영 스위치 `PUT /api/ops/mcp-tool`(운영 설정 `mcpToolsOff`, 감사 남음). 도구별 모의 판정은 따로 두지 않았어요: 도구마다 결과의 `mock`을 보고 실제 자료면 승인 클라이언트에만 보내는 검사가 이미 있어요.
- 노출 명세: `docs/MCP_도구명세.md`(`npm run mcp:spec`). 코드와 다르면 시험이 막아요.

### 1단계: 관리 평면(차별 A·B를 보이게)

- 운영자 화면: 허용 앱 등록·승인·회수(감사 증적), 전사 연결 현황, 사용자별·앱별 강제 끊기, 도구 켜기·끄기
- 월간 보고서(셈만, 내용 없음), 이상 사용 알림
- 연결성: 공개 클라이언트·CIMD·기기별 승인(U1~U3·U6), ChatGPT 허용 → **ADR-15 개정·보안팀 결정 필요**

### 2단계: 도구 넓히기(차별 C, 읽기 + 확인 링크만)

1. `navi_find_team` + 문의 준비 링크 → **ADR-14 개정 필요**(10/31 제안 ③)
2. `my_requests_status`(문의·휴가·예약 상태만, 글·이름 없음)
3. `it_faq_match`, `navi_onboarding`
4. `rooms_my_bookings`, `pantry_find_similar` 공개, `notices_search` 기간 칸
5. 앱 확인 링크 일반화: `/r/:token`이 모듈·동작에 맞는 시트를 열어요(장비 대여·탕비실·문의·휴가). 링크에는 "어느 팀·어느 업무·날짜"만 봉인하고 원문은 넣지 않아요(R13).

### 넣지 않는 것

- MCP 쓰기 도구, 자동 실행 허용 목록의 MCP 확장
- 받은 문의함(보낸 사람 이름·글, 법정 접속기록 대상), 남은 연차 숫자(등급 2, ADR-18)
- MCP elicitation으로 AI 앱 안에서 확인 받기
- 여러 회사를 묶는 MCP, 회사 고르기

## 6. 정할 것(사용자 결정)

1. **ADR-14 개정:** 도구 둘 묶음을 풀고 "읽기 도구 + 앱 확인 링크"로 넓힐지. 넓힌다면 2단계 도구 목록.
2. **문의 글을 AI 앱에서 앱으로 넘기는 방법:**
   - ⓐ 받을 팀만 링크에 넣고 글은 직원이 다시 써요. 안전하지만 불편해요.
   - ⓑ 글을 서버 메모리에 10분쯤 두고 일회용 ID로 꺼내요. "원문은 요청 메모리에만" 선(ADR-10, R13)을 바꿔야 해요.
   - ⓒ 앱이 열리면 클립보드 붙여 넣기를 한 번 권해요.
   - UX 권고: ⓒ로 시작하고 ⓑ는 따로 안건으로 올려요.
3. **순서:** 연결성(ADR-15 개정)과 관리 평면을 도구 확장보다 먼저 할지. 보안팀·UX·아키텍트 모두 "기반 먼저"예요. → **11/2 결정: 연결부터 먼저, 방식은 미리 등록한 공개 클라이언트**(ADR-15 개정, `MCP_UX_TEST.md` 11/2 고침).
4. **일정:** 파일럿 1·2단계는 MCP를 끈 채로 가고 11/30에 동결해요(넓힐후보회의). 0단계를 그 안에 넣을지, 동결 뒤로 미룰지.

## 7. 확인할 것

- 우리 MCP SDK가 따르는 스펙 판. 2026-07-28 판에서 세션이 없어지고(stateless), 동적 등록이 폐기 예정이 되고, 인가 응답 `iss` 검사가 생겼어요. 우리 서버는 이미 상태 없이 POST만 받아요.
- MS 쓰기 기본값·감사, Atlassian 가격, Slack 플랜은 공식 문서로 확정하지 못했어요. 카카오워크·브리티는 공식 MCP를 "찾지 못함"이지 "없음 확인"이 아니에요.
- 게이트웨이 칸은 대부분 공급사 자료예요. 계약·제안서에 쓰기 전에 다시 확인해요.

## 8. 11/2 뒤 논의: "쓰기는 앱에서 한 번" 마찰

- 물음(사용자): 확인 한 번이 간단한 일에도 단계를 하나 늘려서 오히려 번거롭지 않나요?
- 정리: 진짜 비용은 클릭보다 AI 앱 → 브라우저 전환이에요. 자주 하고 되돌릴 수 있는 일(회의실·장비·탕비실)에서 불편이 커요. 문의·휴가는 확인이 자연스러워요. 차별 문구는 "늘 한 번 더 누른다"보다 "무엇을 바로 실행하고 무엇을 확인하는지 목록을 공개하고 회사가 정한다"가 맞아요(앱 채팅은 이미 ADR-19 허용 목록).
- 안: A 지금 원칙 + 마찰 줄이기(링크가 시트를 바로 열기, 상태 조회로 돌려주기) / B MCP에도 허용 목록(CLAUDE.md·ADR-03·14 개정 필요, 보안팀 빨간 선) / C AI 앱 안 확인(elicitation, 이전에 버림).
- **결정(11/2): 보류.** 0단계부터 해요. 파일럿에서 실제 불만 근거를 본 뒤 다시 봐요.
