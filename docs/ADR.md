# 한 줄 데스크 ADR (아키텍처 결정 기록)

- 날짜: 2026-10-23 · 기준: `회의/03_결정.md`(D1~D13, 화면 S1~S6), `회의/05_수정지시.md`(R1~R18), `회의/08_MCP_결정.md`(M1~M7), `회의/02_개발자_2라운드.md`
- 범위: 2주·1명 MVP(F1 묻고 근거 카드, F2 회의실 찾고 확인 예약, F3 같이 채워요) + 읽기 전용 MCP(도구 둘, F1·F2 공통 채널). IT 캡처·FAQ 해결 단계·티켓 초안·MCP 쓰기 도구·알림 모의·공지 인용 요약은 이번 범위 밖이에요.

## 아키텍처 한눈에

1. 브라우저 앱은 탭 셋(묻기 / 같이 채워요 / 내 것)이에요. 입력은 보내기 전에 **브라우저 공통 검사**를 거쳐요. 등급 3·키·토큰은 여기서 멈추고, 이메일·IP는 가린 뒤에만 나가요. 원문은 페이지 메모리에만 있고 URL·브라우저 저장소에 가지 않아요.
2. 묻기 입력은 POST 본문으로 **앞문 라우터**(`/ask`)에 가요. 라우터는 같은 검사를 한 번 더 하고, 규칙 → LLM 한 번으로 종류와 슬롯을 정해요.
3. 라우터는 모듈 넷(navi·notices·rooms·pantry)의 **읽기 기능만** 불러 카드를 만들어요. 쓰기 카드에는 서버가 서명한 짧은 수명의 제안 토큰만 붙여요. `/ask`가 남기는 건 감사 로그(가명 ID·시각·모듈 종류·결과)와 메모리 속 요청 횟수뿐이에요.
4. 사람의 확인은 쓰기마다 한 번이에요. 회의실은 주 버튼이 **plan 저장소**에 plan을 만들고, 확인 시트 버튼이 plan_id로 실행해요. 게시는 공개 미리보기의 [올리기]가 확인이자 실행이에요. +1·총무 확정 같은 고정 버튼은 plan 없이 같은 **실행기**를 거쳐요.
5. 바깥 데이터는 모두 **어댑터** 뒤에 있어요(IdP·디렉터리·회의실 장부·공지·분장표·카탈로그·알림). 모의 어댑터가 하나라도 켜져 있으면 "시연 데이터로 돌아가요" 띠가 떠요. 예약자 이름은 회의실 어댑터에서 멈춰요.
6. LLM은 **AI 게이트웨이** 하나로만 불러요. 등급 0·1만 통과하고(무보관 계약 확인 전엔 등급 0만), 무보관 모델로 고정하고, 요청마다 상태 없이 불러요. 질문 원문은 `/ask` 서버 메모리에서 멈추고 DB·로그·오류 보고·프록시 기록에 가지 않아요.
7. 모든 쓰기와 거절은 **감사 로그**에 남아요. 내용 칸은 없어요.
8. **운영 설정**(끄기 스위치·설정값)을 라우터·도구 레지스트리·실행기가 함께 읽어요. `링크만`이면 링크 카드, `끔`이면 그 종류를 후보에서 빼고 담당 안내로 보내요.
9. 투표자 신원은 pantry DB에서 멈춰요. LLM과 총무 화면에는 수만 가요. 분장표의 사람 이름은 가져오기 단계에서 버려요. (알림과 **알림 주소 표**는 다음 2주예요.)
10. **세션**은 서버에만 있어요. 정해진 간격마다 IdP에 재직을 다시 확인해서 퇴사자를 끊어요.
11. 외부 AI 클라이언트는 **MCP 서버**(`/mcp`, 읽기 도구 둘)에 붙어요. 우리 **인가 서버**가 준 토큰만 받고, 도구는 rooms·notices 읽기 함수를 부를 뿐 LLM과 DB 쓰기는 없어요. 결과는 클라이언트 모델로 가서 등급 1이 우리 손을 떠나요. 그래서 보안팀 허용 목록이 빈 동안에는 모의 데이터로만 켜요. 예약은 링크를 통해 앱 확인 시트에서만 돼요.

### ADR-01 앱 형태
- 상태: 채택(2026-10-23 M1로 수정) · 날짜: 2026-10-23 · 관련: D1, D11, M1, M2, M6, F1~F3, S1~S6
- 맥락: 원래 주제는 "회사생활 MCP"였어요. 처음엔 MCP 인가가 2주를 먹을까 봐 미뤘지만, 사용자가 2주 안에 읽기 전용 MCP(회의실 조회·공지 찾기)를 넣기로 했어요(M1). 외부 AI 클라이언트는 확인 시트와 공통 검사를 우리 손 밖으로 가져가니, 쓰기는 계속 앱 안에만 둬야 해요.
- 결정
  - 웹앱 하나 + 서버 하나의 모듈형 모놀리스예요. 공통 바닥(인증·세션·감사 로그·게이트웨이·plan) 위에 navi·notices·rooms·pantry 모듈을 얹어요.
  - 모듈은 자기 표와 쓰기 경로만 가져요. 다른 모듈 표는 읽지도 쓰지도 않아요.
  - 도구 레지스트리: 도구마다 `{이름(모듈 접두어 + 동작, 예: rooms_find_free), 입력 스키마, 출력 스키마, 필요 권한, 읽기/쓰기, 모듈, MCP 공개 여부}`. 허용 목록·MCP 도구 목록·시험·문서가 이 표 하나를 써요.
  - **읽기 전용 MCP 서버를 2주 안에 열어요.** 도구는 `rooms_find_free`·`notices_search` 둘뿐이에요(ADR-14). 인가는 우리 인가 서버가 해요(ADR-15). 쓰기 도구는 MCP에 없고, 회의실 결과엔 앱 확인 링크만 줘요.
  - MCP에 3일을 쓰려고 처음부터 줄여요(M6): 공지는 찾기 + 원문 링크만(요약 끔), S5는 목록만, 알림 모의는 다음 2주, 판 실시간은 몇 초마다 새로고침. 그래도 모자라면 9일 차에 회의실 쓰기를 조회 + 그룹웨어 링크로 낮춰요(D13 ③).
  - 스택은 TypeScript(React + Node)와 PostgreSQL이에요. Postgres는 ADR-06·07이 기대는 겹침 제약과 행 잠금 때문이에요.
- 고려한 대안: 모든 기능을 MCP로(MCP 바닥) → 확인 시트·공통 검사·판 화면이 클라이언트로 넘어가요. / MCP를 2주 뒤로 → 사용자 결정(M7)과 달라요. / 메신저 봇 중심 → 판·총무 화면을 못 담고, 공개·비공개 탭 구분이 안 돼요. / 모듈마다 따로 앱 → 공통 바닥을 세 번 만들어요.
- 결과 · 좋은 점: 배포·세션이 하나라 보안 바닥을 한곳에서 지켜요. 사내 AI 앱에서도 회의실·공지를 찾을 수 있고, 사용자별 OAuth 인가라는 깊게 팔 몫이 생겨요. F3는 모듈 경계 덕에 혼자 설 수 있어요(D1).
- 결과 · 감수할 점: 공지 요약·알림·판 실시간이 이번엔 빠져요. MCP 결과가 클라이언트 모델로 가는 건 허용 목록이라는 정책에 기대요(ADR-15).
- 결과 · 다시 볼 조건: 다른 클라이언트(Copilot Studio·Claude Code)를 허용하거나 MCP 쓰기 도구를 열 때예요. 그때도 쓰기는 plan + 앱 확인 링크만이에요.

### ADR-02 앞문과 의도 라우팅
- 상태: 채택 · 날짜: 2026-10-23 · 개정: 2026-10-26(사용자 결정: 앞문 없앰, 기능별 페이지) · 관련: D4, F1~F3, S1, S2
- 개정(2026-10-26)
  - 맥락: 처음 쓰는 직원 관점 점검에서 "첫 화면에서 무엇을 할 수 있는지 바로 알 수 없다"가 가장 컸어요. 입력창 하나만 보여서 회의실·탕비실도 된다는 걸 예시 칩을 보고서야 짐작했어요. 사용자가 담당 찾기를 묻기에서 떼고, 기능마다 페이지를 두기로 정했어요(이후 기능별로 독립 기능을 넣기 위해서예요).
  - 결정: 앞문(S1 묻기)을 없애요. 아래 탭은 홈 · 담당 찾기 · 회의실 · 공지 · 같이 채워요 · 내 것이에요. 홈은 기능 안내 카드(설명·예시 문장·열기)와 내 예약·내 요청 요약이에요. 꺼진 모듈의 탭과 안내 카드는 숨겨요(ADR-12).
  - 기능 페이지(담당 찾기·회의실·공지)는 자기 입력 칸이 있고, `POST /api/ask`에 자기 종류(`kind`)를 정해서 보내요. 서버 라우터는 그 종류를 그대로 쓰고(되묻기 없음) 슬롯만 뽑아 그 모듈로 보내요. 원문 비저장·공통 검사·요청 횟수·감사 로그는 그대로예요.
  - 결과는 시트 대신 페이지 안에 보여요. 회의실 조건 칩을 고쳐 다시 찾으면 그 자리에서 바뀌어요.
  - "틀렸어요 → 종류가 달라요", 공지 [담당 찾기에서 찾기], 판 [담당 찾기로 옮기기]는 같은 문장을 다른 기능 페이지로 옮기고 그 페이지에서 바로 찾아요. 문장은 앱 메모리로만 넘겨요(R13). 홈 예시 문장은 입력 칸에 채우기만 해요.
  - 아래 2026-10-23 결정 중 확신 계산·칩 되묻기는 앱 화면에서 쓰지 않아요(종류를 사용자가 고르니까요). `/api/ask`에 종류 없이 보내면 예전처럼 분류해요.
  - 처음 고려한 대안 "홈 + 모듈 메뉴판"을 고른 셈이에요. 감수할 점: "어디서 해요?"를 종류를 모른 채 물을 곳이 없어요. 모르면 담당 찾기에서 물어요(못 찾으면 "여기로 물어보세요").
- 2026-10-23 결정(앞문이 있을 때)
- 맥락: 입력창 하나가 담당·공지·회의실·탕비실을 받아요. 잘못 나누면 사용자는 엉뚱한 카드를 받아요. 규칙만으로는 다른 말("법카 잃어버림")을 못 잡고, LLM만으로는 흔들려요.
- 결정
  - 순서: 공통 검사 → 규칙 → LLM 한 번(구조화 출력) → 확신 계산 → 모듈 읽기.
  - LLM 출력 스키마: `kind`(`navi | notices | rooms | pantry | unknown`), `slots`, `ambiguous`(참·거짓). 슬롯은 rooms `{날짜, 시작, 길이, 인원, 장비[], 층}`, pantry `{품목 이름}`이에요. navi·notices는 슬롯이 없어요.
  - 한글 ↔ 코드: 담당 = `navi`, 공지 = `notices`, 회의실 = `rooms`, 탕비실 = `pantry`, 모름 = `unknown`.
  - 확신 높음: 규칙이 같은 종류를 가리키거나 아무것도 안 가리키고, `ambiguous`가 거짓이고, `kind`가 `unknown`이 아닐 때예요. 그 밖은 낮음이에요.
  - 낮음이면 S2 머리의 종류 칩 최대 3개 + "다른 거예요"로 되물어요. 숫자 확률은 화면에 넘기지 않아요.
  - `unknown`은 담당 안내(navi, 읽기 전용)로 가요.
  - 칩을 바꾸면 브라우저가 페이지 메모리의 같은 문장으로 그 모듈을 다시 불러요. 서버는 문장을 남기지 않아요.
  - 끄기 스위치(ADR-12): `링크만`인 종류는 그대로 분류하고 링크 카드를 줘요. `끔`인 종류는 규칙과 `kind` 후보에서 빼고, 그래도 걸리면 담당 안내로 보내요.
- 고려한 대안: 규칙만 → 다른 말과 줄임말에서 실패해요. / LLM만 → 같은 입력에 다른 답이 나와도 알아챌 길이 없어요. / 홈 + 모듈 메뉴판 → 사용자가 메뉴를 골라야 해서 "어디서 해요?" 문제를 못 풀어요.
- 결과 · 좋은 점: 어떤 종류로 가도 결과는 제안 카드라 쓰기 사고가 안 나요. 기본 출구가 읽기 전용이에요.
- 결과 · 감수할 점: 입력마다 LLM 한 번 비용과 지연이 들어요. 아직 재 보지 않았어요(10일 차 측정).
- 결과 · 다시 볼 조건: 경계 문장 골든셋에서 되묻기가 너무 자주 뜨면 규칙 사전을 넓혀요.

### ADR-03 쓰기 실행 경계(plan)
- 상태: 채택 · 날짜: 2026-10-23 · 관련: D5, D6, D7, D8, R2, R5, R7, S2, S4
- 맥락: 공지 본문이나 요청 이름 속 지시문이 LLM을 거쳐 쓰기를 부를 수 있어요. 확인 버튼을 눌렀을 때 실행되는 값이 사용자가 본 값과 같아야 해요.
- 결정
  - LLM에는 쓰기 도구를 주지 않아요. LLM 결과는 모두 "제안"이에요.
  - `/ask`는 쓰기 카드에 **제안 토큰**만 붙여요. 서버가 서명하고 수명이 짧아요(운영 설정). 안에는 사용자·모듈·동작·대상·슬롯 값(탕비실은 AI가 뽑은 품목 이름)·만료가 있어요. DB에는 쓰지 않아요.
  - **사람의 확인은 쓰기마다 정확히 한 번이에요(R2).**
    - 회의실: 후보 카드 주 버튼 → rooms 쓰기 경로가 토큰을 검증하고 plan을 만들어 확인 시트를 열어요 → [예약하기]가 plan_id만 보내 실행해요.
    - 게시: 공개 미리보기가 곧 확인이에요. [올리기]가 토큰과 확정한 이름을 보내면 서버가 재검사 뒤 plan 만들기와 실행을 한 번에 해요(ADR-04). [올리지 않기]면 아무것도 남지 않아요.
    - 고정 버튼 쓰기(+1·거두기·예약 취소·총무 합치기·되돌리기·따로 두기·주문안 확정·분장표 파일 다시 올리기·AI 앱 연결 끊기·모든 기기 로그아웃): plan 없이 같은 실행 함수(권한·상태 재검사·멱등 키)를 거쳐요. 확인 시트가 있는 동작은 시트의 버튼이 곧 실행이에요.
  - plan 칸: plan_id(멱등 키 겸용), 가명 사용자 ID, 모듈, 동작, 매개변수(검증된 구조 값만, 회의실은 조건 슬롯 포함, 자유 문장 없음), 만든 시각, 만료 시각(운영 설정, 시험에선 짧게), 상태, 결과 참조.
  - 상태 전이: `제안됨 → 실행 중 → 완료 | 막힘`, `제안됨 → 만료 | 취소`. `제안됨 → 실행 중`은 "상태가 제안됨일 때만 바꾸기"로 해서 한 번만 이겨요. 버튼은 누르면 바로 잠기고, 같은 plan_id나 멱등 키가 다시 와도 결과만 돌려줘요.
  - 실행 때 다시 검사해요: 세션 사용자 = plan 주인, 권한 다시 계산, 만료, 운영 설정, 대상 상태(빈 방·묶음 버전).
  - 만료된 plan을 확인하면 실행하지 않아요. 저장된 조건 슬롯으로 다시 찾아 새 후보와 새 토큰을 돌려줘요("시간이 지나 다시 찾았어요").
  - 막힘은 확인 순간 재검사에서만 써요. 이유 코드: `다른 예약` · `올릴 수 없는 글자` · `기능 꺼짐`.
  - 카드 머리 라벨(제안·확정·안내·막힘)과 대응: 제안 카드·확인 시트 = 제안, 완료 = 확정, 막힘 = 막힘, 읽기 카드·만료 뒤 다시 찾기 = 안내. 실행 중은 버튼 글자("예약하는 중")로만 보여요.
- 고려한 대안: LLM 도구 호출로 바로 실행 → 주입 한 번이 쓰기가 돼요. / 확인 버튼이 매개변수를 같이 보냄 → 화면과 실행 값이 달라질 수 있어요. / `/ask`가 plan을 바로 저장 → 묻기 경로가 DB에 쓰게 돼 ADR-04와 부딪혀요.
- 결과 · 좋은 점: 쓰기 경로가 모듈별로 한 군데라 시험하기 쉬워요.
- 결과 · 감수할 점: 회의실 쓰기는 왕복이 한 번 늘어요. 제안 토큰 서명 키를 관리해야 해요.
- 결과 · 다시 볼 조건: MCP 쓰기 도구를 열 때도 이 plan을 그대로 써요(앱 확인 링크).

### ADR-04 묻기와 공개 게시 분리
- 상태: 채택 · 날짜: 2026-10-23 · 관련: D4, D7, R2, F3, S1, S2, S3
- 맥락: 같은 사람이 묻기 탭에는 비공개 질문을, 같이 채워요 탭에는 공개 요청을 써요. 비공개 질문이 판에 올라가는 사고를 화면 문구만으로 막을 수는 없어요.
- 결정
  - `/ask`와 `/pantry/draft`는 저장하지 않아요(감사 로그와 메모리 속 횟수만). 두 경로의 DB 역할에는 판 표의 INSERT·UPDATE 권한이 없어요(가능하면 역할 분리, 안 되면 코드 의존 금지 + 시험).
  - 탕비실 의도면 `/ask`는 게시 초안(AI가 뽑은 품목 이름 + 비슷한 열린 품목 + 제안 토큰)만 돌려줘요. 입력 원문은 초안에도 없어요. 비슷한 열린 품목이 있으면 같은 품목 카드([여기에 +1], 고정 버튼 쓰기)를 먼저 보여 줘요.
  - 같이 채워요 탭 요청 쓰기 칸은 `/pantry/draft`로 같은 초안을 받아요. 담당 질문처럼 보이면 "이건 담당 안내가 맞아 보여요" + [묻기로 옮기기]이고, 글은 앱 메모리 상태로만 옮겨요(URL·저장소 안 씀).
  - 공개 미리보기(S2)가 게시 확인이에요: "'코카콜라 제로'라는 이름으로 우리 층 사람들에게 보여요. 내 이름은 안 보여요." [올리기] / [올리지 않기], 기본 선택 없음. 이름은 고칠 수 있어요.
  - [올리기]는 토큰과 확정한 이름만 보내요. 서버는 토큰(사용자·만료)을 검증하고, 공통 검사·전화번호·이메일·사람 이름 패턴·횟수·표 상한을 다시 본 뒤 카드와 작성자 표 1개를 한 트랜잭션으로 만들어요(멱등 키 = 토큰 ID).
  - 그사이 비슷한 품목이 생겼으면 게시 대신 같은 품목 카드를 돌려줘요. 토큰이 만료됐으면 고친 이름으로 새 토큰을 돌려주고, 사용자가 한 번 더 눌러요.
  - 판에 저장되는 건 품목 이름·층·가명 작성자 ID·시각뿐이에요. 합치기도 품목 이름으로 해요.
  - "틀렸어요" 기록은 따로 된 피드백 경로로 가요. 스키마는 ID·라벨 칸뿐이고, 자유 문장 칸이 오면 거부해요(ADR-09).
- 고려한 대안: 원문 문장을 판에 그대로 게시 → 비공개 내용이 섞일 수 있어요. / 화면 경고만 → 사용자가 읽지 않으면 막지 못해요.
- 결과 · 좋은 점: 공개되는 글자는 "사용자가 확인 시트에서 본 그 문자열"뿐이에요.
- 결과 · 감수할 점: "회의 많은 날엔 커피 더" 같은 사연은 판에 남지 않아요.
- 결과 · 다시 볼 조건: 총무가 요청 사연이 필요하다고 하면, 공개 메모 칸을 따로 두고 같은 검사를 걸어요.

### ADR-05 바깥 데이터 연동
- 상태: 채택 · 날짜: 2026-10-23 · 관련: D6, D10, D11, R6, R17, F1~F3
- 맥락: 국내 그룹웨어에서 회의실 빈 시간을 읽는 공식 API를 못 찾았어요(기존 제품 B). 분장표·카탈로그는 파일로만 있어요. 2주 안에 사내 IdP 등록과 무보관 계약이 끝날지도 몰라요.
- 결정
  - 어댑터: IdP(모의 OIDC → 사내 IdP), 디렉터리(층·부서), 회의실 장부, 공지 원천, 분장표 가져오기, 카탈로그 가져오기, 알림.
  - 어댑터는 capabilities를 돌려줘요. 모든 어댑터는 `모의: 참 | 거짓`, 회의실 장부는 `빈 시간: 직접 | 계산 | 없음`, `쓰기: 켬 | 끔`도 알려요. 화면은 "현황 HH:MM 기준"을 붙여요.
  - 모의 어댑터가 하나라도 켜져 있으면 앱 위쪽에 "시연 데이터로 돌아가요" 띠 하나를 붙여요. 누르면 어떤 데이터가 모의인지 보여 줘요(R6).
  - 역할(R17): 총무·운영자는 IdP 그룹에서 받아요(없으면 운영자가 관리하는 역할 표). 분장표 주인은 디렉터리 부서 클레임이 행의 주인 부서와 같을 때예요. 진입점 숨김과 별개로 서버가 요청마다 (역할, 층, 모듈, 동작)으로 검사해요.
  - 2주 출처: 회의실 = 모의 장부, 분장표·공지·카탈로그 = 파일 가져오기. 알림 어댑터는 다음 2주예요(M6).
  - 실제 연결 후보: 공지는 네이버웍스 Board API(읽기), 로그인은 네이버웍스 OIDC, 회의실은 M365라면 Graph 일정 조회(getSchedule)예요. 모두 회사 그룹웨어가 정해진 뒤의 일이에요.
  - 분장표 가져오기는 사람 이름 칸을 버리고 팀·창구만 남겨요(D9).
- 고려한 대안: 그룹웨어 직접 호출 → 회사마다 API가 달라 모듈 코드가 흔들려요. / 처음부터 실제 연동 → 빈 시간 API가 없어서 회의실은 시작할 수 없어요.
- 결과 · 좋은 점: 그룹웨어가 정해져도 어댑터 하나만 바꿔요.
- 결과 · 감수할 점: 시연은 모의 데이터라 "실제로 되나"에는 답하지 못해요.
- 결과 · 다시 볼 조건: 사용자 확인 2번(그룹웨어 종류)이 정해지면 그 어댑터를 먼저 만들어요.

### ADR-06 회의실 충돌과 예약자 비노출
- 상태: 채택 · 날짜: 2026-10-23 · 개정: 2026-10-26(회의실 둘러보기) · 관련: D6, R5, F2, S2, S6
- 개정(2026-10-26, 사용자 결정): 회의실 페이지에 "모든 회의실"(방 카드: 그림·정원·지금 상태 → 방 자세히: 설비·하루 일정·이 시간 예약)을 둬요. 하루 일정은 30분 칸이고, 남의 예약은 "예약됨"과 시간 구간만 보여요(예약자·회의 제목·가명 ID 없음). 내 예약에만 [취소]가 붙어요. "회의실 현황은 물리 보안 정보"라는 맥락은 그대로라서 로그인한 직원만 보고, MCP 출력에는 여전히 방별 일정이 없어요(ADR-14). 방 사진·설비는 장부가 주는 값이고, 시연은 그림(`apps/web/public/rooms`)과 가상 설비예요.
- 맥락: 두 사람이 같은 방을 동시에 확정할 수 있어요. 회의실 현황은 물리 보안 정보이고, 예약자 이름은 개인정보예요.
- 결정
  - 모의 장부가 원본이에요. 예약 표: 방 ID, 시간 구간(범위 타입), 가명 예약자 ID, plan_id(유일). 방 ID 같음 + 시간 겹침을 막는 겹침 제약을 둬요(btree_gist 확장 사용).
  - 취소한 예약은 예약 표에서 지우고 이력 표로 옮겨요. 그래서 겹침 제약에 조건을 달 필요가 없어요.
  - 확정 = 재확인이에요. 실행기가 INSERT하고 제약이 막으면 막힘 카드(이유 `다른 예약`) + 대안 최대 2개를 돌려줘요. 결과 카드에 "HH:MM에 다시 확인하고 예약했어요".
  - 처음부터 빈 방이 없으면 막힘이 아니에요. 안내 카드 "그 시간엔 빈 방이 없어요" + 가까운 시간 대안 최대 2개예요(R5).
  - 대안 규칙: 같은 방 앞뒤 가까운 시간 → 같은 층 조건 맞는 다른 방 → 다른 층 순으로 최대 2개. 대안마다 새 제안 토큰을 붙여요. 만료 뒤 다시 찾기는 plan의 조건 슬롯으로 해요(ADR-03).
  - 범위: 내 이름으로 하루 안의 한 구간만, 반복·여러 날·대리 예약 없음.
  - 화면용 타입에는 예약자 칸이 아예 없어요. 칸은 방·층·인원·장비·구간·상태(`비어 있음 | 예약됨 | 내 예약`)뿐이에요.
  - 파일럿에서는 실제 연결이 확인되기 전까지 회의실 쓰기를 꺼요(이중 장부 방지, ADR-12).
- 고려한 대안: 앱 코드에서 "조회 후 쓰기" → 두 요청 사이 틈에서 둘 다 성공할 수 있어요. / 그룹웨어를 원본으로 → 빈 시간 읽기 API가 없어요.
- 결과 · 좋은 점: 동시 확정에서 한 명만 성공하는 걸 DB가 보장해요.
- 결과 · 감수할 점: 모의 장부와 실제 그룹웨어가 따로 놀아요. 그래서 파일럿 쓰기는 꺼요.
- 결과 · 다시 볼 조건: 실제 장부에 연결하면 진실은 그쪽이에요. 쓰기 뒤 다시 읽어 확인하는 단계를 더해요(네이버웍스 설비 겹침 응답은 확인 필요).

### ADR-07 표·묶음 데이터 모델
- 상태: 채택 · 날짜: 2026-10-23 · 관련: D8, R3, R14, R15, R16, F3, S3, S4
- 맥락: "제로콜라"와 "코카콜라 제로 355"를 합칠 때 표를 어떻게 세는지, 되돌리면 어떻게 되는지, 동시에 손대면 어떻게 되는지가 F3의 핵심 질문이에요.
- 결정
  - 테이블
    - 요청 카드: 카드 ID, 층, 품목 이름, 카탈로그 품목 ID(없을 수 있음), 가명 작성자 ID, 상태(`열림 | 주문됨`), 묶음 버전, 만든 시각.
    - 투표: (가명 사용자 ID, 카드 ID) 유일, 만든 시각.
    - 합치기 기록: 합칠 카드, 대표 카드, 확정한 총무, 시각, 되돌린 시각(없을 수 있음).
    - 같은 상품 표시: 카드 쌍, 출처(AI·규칙), 상태(`표시 중 | 합침 | 따로 둠`).
    - 주기: (층, 주기 번호), 상태(`열림 | 닫힘`), 1인 품목 수 상한(총무가 정함).
  - 묶음 = 되돌리지 않은 합치기 기록으로 이은 카드 묶음이에요. 대표는 카탈로그에 맞춘 카드, 같으면 먼저 만든 카드예요.
  - 합치기 확정·되돌리기·따로 두기는 총무만 S4에서 해요. 확정 전에는 "같은 상품 같아요"만 보여 주고 표는 합치지 않아요.
  - "같은 상품 같아요" 계산(R15): 게시 순간 pantry 경로가 AI로 같은 층 열린 품목과 비교해 표시 행을 만들어요. 판과 총무 제안함에 같이 보여요. 총무가 S4를 열 때 남은 후보를 한 번 더 모아요. 묻기의 같은 품목 확인은 읽기만 해요. `따로 둠` 쌍은 다시 제안하지 않아요.
  - 셈: 묶음 표 = 묶음 안 카드들에 표를 준 서로 다른 사람 수(사람 × 묶음). 게시하면 작성자 표 1개가 같이 생겨요.
  - +1은 대표 카드에 붙어요. 이미 그 묶음에 표가 있으면 아무 일도 없어요. 거두기는 그 사람이 묶음 안에 가진 표를 모두 지워요.
  - 상한(R14): "열린 묶음 중 내 표가 있는 묶음 수"예요(넘어온 표·작성자 표 포함). +1과 게시 순간에만 검사해요. 합치기가 풀려 넘친 경우는 표를 그대로 두고 화면이 안내해요.
  - 주기(R16): 주문안 확정 때 들어간 묶음은 `주문됨`(표 닫힘)이 되고, 그 층 주기가 닫히고 새 주기가 열려요. 나머지 카드와 표는 그대로 넘어가요. 따로 마감 시각은 없어요.
  - 동시성(R3): 표 쓰기(게시·+1·거두기)는 그 사람 단위로 잠가요(같은 사람의 연타·동시 +1이 상한을 넘지 않게). 표 쓰기는 묶음 버전을 올리지 않아요. 합치기·되돌리기는 관련 대표 카드 행을 ID 순서로 잠그고, 화면이 본 묶음 버전과 다르면 409("다른 총무가 먼저 이 품목을 바꿨어요. 새로 불러왔어요")예요. 성공하면 묶음 버전을 올려요. 직원 판은 몇 초마다 새로고침해서 바뀐 묶음을 받아요(M6, 실시간 SSE는 다음 2주).
- 불변식: I1 묶음 표 = 서로 다른 사람 수 · I2 한 사람 한 카드 한 표 · I3 합치기·되돌리기는 투표 행을 바꾸지 않음 · I4 거두기 뒤 그 묶음에 내 표 없음 · I5 합치기 연결에 순환 없음 · I6 `주문됨` 묶음에 새 표 없음 · I7 검사 순간 상한을 넘는 +1·게시 0건 · I8 표 쓰기는 409를 만들지 않음.
- 고려한 대안: 표를 대표 카드로 옮기기 → 되돌리면 누가 어디에 눌렀는지 잃어요. / 직원 누구나 합치기(기획자 안) → 동시에 쓰는 사람이 늘고 잘못 합치기를 막기 어려워요(D8 2:1).
- 결과 · 좋은 점: 되돌리면 카드별 표가 합치기 전과 같아요. 합치기 순서와 상관없이 셈이 같아요.
- 결과 · 감수할 점: 합치기가 풀리면 상한을 넘는 사람이 생길 수 있어요(R14, 화면 안내). 사람 단위 잠금이라 한 사람의 빠른 연타는 차례로 처리돼요.
- 결과 · 다시 볼 조건: 총무 확정이 밀려 판이 같은 품목으로 지저분해지면, 확정 권한을 넓힐지 기획에서 다시 봐요.

### ADR-08 주문안 풀이와 설명
- 상태: 채택 · 날짜: 2026-10-23 · 개정: 2026-10-26(D8 1단계 보정) · 관련: D8, R1, F3, S4
- 맥락: 예산 안에서 층마다 최소 몫을 지키며 표를 많이 담아야 해요. 총무는 "왜 3층은 이만큼인지"를 알아야 고쳐서 확정할 수 있어요.
- 결정
  - 입력: 전체 예산, 층별 최소 몫 금액(총무 입력, 처음엔 같은 금액), 열린 묶음(층·표 수·카탈로그 단가·묶음 단위). 수량은 기본 한 묶음 단위이고 총무가 고쳐요.
  - 층 목표 = min(최소 몫, 그 층 카탈로그 요청 금액 합)이에요.
  - 층마다 "목표를 채우는 가장 싼 묶음 조합"의 금액(최소 비용)을 정확히 구해요(동적 계획법, 금액은 묶음 금액들의 최대공약수 단위). 층 번호 순으로 최소 비용을 더해 예산 안에 드는 층이 "꼭 채울 층"이에요. 정수 계획이 "채울 수 있음"이면 모든 층이 꼭 채울 층이에요.
  - 1단계(R1, D8 1단계 보정): 층 번호 순으로 그 층 묶음을 "표 ÷ 단가" 큰 순으로 넣어요. 넣은 뒤에도 남은 예산으로 "이 층의 남은 묶음으로 목표 채우기 + 뒤에 올 꼭 채울 층의 최소 비용"을 낼 수 있을 때만 넣고, 아니면 건너뛰어요. 층 금액이 목표에 닿으면 다음 층으로 가요(이유 코드 `층 최소 몫`). 이 확인이 정확해서 꼭 채울 층은 늘 목표에 닿아요.
  - 2단계: 남은 예산을 모든 층의 남은 묶음에 같은 순서로 채워요(`표 대비 값`). 못 넣은 건 `예산 초과로 뺌`, 카탈로그에 없는 건 `카탈로그에 없음`이에요.
  - 경고와 잠금(R1): 예산 < 최소 몫 합이면 주문안은 만들고 경고 + 확정 잠금이에요(총무가 예산이나 최소 몫을 고쳐야 풀림). 요청 금액 < 최소 몫인 층은 있는 만큼만 담고 "요청이 모자라 최소 몫을 못 채웠어요" 경고예요(잠그지 않음).
  - 묶음 단위 때문에 목표에 못 닿은 층도 경고를 붙여요. 못 채운 층에는 모두 경고가 있어야 해요.
  - 총무가 줄을 고치면 검사기를 다시 돌려요. 예산을 넘으면 확정을 잠가요. 고친 줄의 설명은 틀 문장으로 바꾸고 "총무가 고침" 라벨을 붙여요(이유 코드 칩은 그대로).
  - 설명: LLM에는 줄마다 `{줄 ID, 품목 이름, 층, 표 수, 금액, 이유 코드, 순위}`만 줘요. 투표자 정보는 안 줘요. LLM은 줄마다 한 문장을 돌려줘요.
  - 숫자 검사: 문장 속 숫자가 모두 그 줄 값 안에 있어야 해요. 한글 수사(세, 다섯 등)가 있거나 줄이 빠지면 틀 문장으로 바꿔요.
  - 정수 계획(highs-js)은 시험에서만 써요(D8). 같은 입력에서 최적값과 "모든 층 최소 몫을 채우는 배정이 있는지"를 구해 주문안과 비교해요. "채울 수 있음"인데 못 받은 층이 하나라도 나오면 시험 실패예요. 표 합 차이는 기록만 해요.
- 고려한 대안: 운영에서 정수 계획 → 최적이지만 "왜 이 줄인지"를 순서로 설명하기 어려워요. / 탐욕법이 못 채운 입력만 정수 계획으로 다시 풂(처음 정한 다시 볼 조건의 안) → highs를 운영 의존성으로 올리고, 이유 코드·설명을 정수 계획 결과에도 맞춰야 해요(10/26 D8에서 1단계 보정을 골랐어요). / 다른 층이 못 채운 목표 금액만 남겨 두는 처음 규칙 → 묶음 단위 때문에 실제로 드는 돈이 더 커서, 무작위 비교에서 "채울 수 있음" 입력의 약 10%에서 층 몫을 못 채웠어요. / LLM이 주문안을 짬 → 예산·최소 몫을 지킨다는 보장이 없어요. / 예산이 모자라면 주문안을 안 만듦 → 총무가 무엇을 고칠지 볼 수 없어요(R1).
- 결과 · 좋은 점: 줄마다 이유 코드가 있어 총무가 고칠 곳을 알아요. 규칙 검사기로 예산·최소 몫을 늘 확인해요.
- 결과 · 감수할 점: 표 합은 최적이 아닐 수 있어요(무작위 800개, "채울 수 있음" 입력에서 최적과 평균 0.5~0.8% 차이). 묶음 단위 때문에 어떤 배정으로도 모든 층의 최소 몫을 못 맞추는 입력이 있어요. 그래서 "못 받은 층 0건"은 정수 계획이 "채울 수 있음"이라고 한 입력에서 세요. 그런 입력과 예산 < 최소 몫 합인 입력에서는 층 번호 순으로 채울 수 있는 층부터 채우고, 나머지 층에는 경고를 붙여요. 이때 표 합은 최소 몫을 무시한 최적보다 평균 7~17% 낮아요.
- 결과 · 다시 볼 조건: 2026-10-26에 성립했어요(정수 계획은 채우는데 처음 규칙이 못 채운 입력이 넓은 분포 39개·파일럿 모양 35개). 사용자가 D8을 1단계 보정으로 바꿨고, 같은 무작위 입력에서 못 받은 층은 0건이에요. 앞으로는 시험이 실패로 막아요. 다 못 채우는 입력에서 "층 번호 순"이 불공평하다는 의견이 나오면, 채우는 층 수를 가장 많게 고르는 방식을 다시 봐요.

### ADR-09 근거 강제
- 상태: 채택 · 날짜: 2026-10-23 · 관련: D9, D10, R8, R9, R10, M6, F1, S2, S5
- 맥락: 담당 카드가 지어낸 부서나 기간을 말하면 사용자가 엉뚱한 곳에 가요. 공지 요약도 원문에 없는 말을 하면 안 돼요.
- 결정
  - 분장표 행: 행 ID, 업무, 담당 팀, 창구(대표 메일·채널·창구 이름), 지금 할 일 단계, 처리 기간, 다른 말, 개정일, 주인 부서. 사람 이름 칸은 없어요(가져오기에서 버림).
  - 담당 카드: 검색으로 후보 행을 고르고, LLM은 구조화 출력으로 후보 enum 중 행 ID 하나 또는 `없음`만 골라요. 화면은 그 행 원문 칸을 그대로 그려요. `/ask`는 다른 후보 행 최대 3개도 같이 돌려줘서 "틀렸어요" 시트가 써요. `없음`이면 "여기로 물어보세요"(총무 창구) 카드이고, 따로 기록하지 않고 감사 로그 결과 "못 찾음"으로만 세요(10명 이상 묶음 통계).
  - 공지 카드: 이번 2주는 공지 요약 스위치를 꺼 둬요(M6). 카드는 제목·게시일·원문 링크만 보여 주고, 맞는 공지가 없으면 "못 찾았어요" 카드예요. 요약을 켤 때 규칙: 후보 공지를 문서로 넣고 인용 기능을 켜요. 인용이 붙은 문장만 1~2줄로 보여 주고, 인용 없는 문장은 버려요. 인용 기능은 구조화 출력과 같이 못 써서 공지는 구조화 출력을 쓰지 않아요.
  - 담당 카드에 관련 공지 링크는 붙이지 않아요. 모듈 사이 읽기를 새로 만들지 않아요(R10).
  - "틀렸어요"(R8): 선택지는 [다른 담당이에요] [목록에 없어요] [안내 내용이 바뀌었어요] [종류가 달라요]예요. 기록은 (예측 종류, 고친 종류, 예측 행, 고른 행, 이유 코드, 시각)만이에요. 사용자 ID·가명 ID·질문 원문은 없어요. 피드백 경로로 따로 보내요(ADR-04).
  - S5(R9): 기록은 분장표를 자동으로 바꾸지 않아요. 예측 행의 주인 부서 S5에 묶음으로 보여요. 분장표 주인이 고쳐 저장해야 반영되고 개정일이 올라가요. 이번 2주는 S5가 목록만이라 고치는 길은 분장표 파일 다시 올리기예요(M6). 행 직접 고치기와 "다른 말" 칸 화면은 다음이에요.
  - "개선용으로 보내기"는 만들지 않아요.
- 고려한 대안: LLM이 카드 문장을 씀 + 사후 검사 → 지어낸 문장을 다 잡는다는 보장이 없어요. / 인용 기능만으로 담당 카드 → 인용 사이 문장은 자유라 기간·창구를 지어낼 길이 남아요.
- 결과 · 좋은 점: 카드의 사실은 모두 분장표나 공지 원문이에요. 지어낼 길이 구조적으로 없어요.
- 결과 · 감수할 점: 원문 없이 라우팅·검색을 고치는 데 한계가 있어요. 분장표 주인이 "다른 말" 칸을 채워야 좋아져요.
- 결과 · 다시 볼 조건: 보안팀이 동의 기반 문장 수집을 허락하면 다시 봐요.

### ADR-10 AI 호출과 원문 비보관
- 상태: 채택 · 날짜: 2026-10-23 · 관련: D5, D9, R6, R11, R12, R13, M5, M6, 공통 바닥, F1~F3
- 맥락: 회사 업무 내용을 외부 AI로 보내지 않는 게 원칙이에요. 모듈 넷이 같은 LLM을 쓰면 대화 기억이나 로그를 타고 등급이 섞일 수 있어요.
- 결정
  - LLM 호출은 게이트웨이 하나로만 해요. 호출마다 모듈·목적·데이터 등급을 붙이고, 등급 2 이상이면 거부해요.
  - 모델은 무보관이 되는 모델로 고정해요. Anthropic 문서상 "Covered Models"는 30일 보관이 필요해 무보관이 안 돼요. Files API·Batch·MCP connector처럼 무보관 대상이 아닌 기능은 쓰지 않아요. 구조화 출력은 "JSON 스키마만 최대 24시간 캐시"인 조건부 대상이라 스키마에 사내 정보를 넣지 않아요.
  - 무보관 계약(R6): 확인 전에는 게이트웨이가 등급 0만 통과시켜요. 그동안 측정은 가상(등급 0) 분장표·질문으로만 해요. 실제 직원 파일럿은 계약 확인 뒤에 시작해요.
  - 무상태: 요청 하나에 호출 하나, 모듈 사이 대화 기억 없음. 되묻기는 브라우저가 같은 문장으로 다시 불러요.
  - 모듈 호출에는 그 모듈 허용 목록의 자료만 넣어요(레지스트리 기준). 쓰기 도구는 어디에도 없어요.
  - 원문이 샐 틈(R13): 오류 보고·분석·세션 녹화 도구는 쓰지 않거나 본문·입력값 칸을 빼요. 프록시·APM의 요청 본문 기록은 꺼요. 원문은 URL에 넣지 않고 POST 본문으로만 보내요. 로거는 본문 칸을 빼요.
  - 감사 로그: 가명 ID(IdP 식별자에 서버 비밀 키로 만든 값)·시각·모듈·동작·결과·plan_id예요. `/ask`는 가명 ID·시각·모듈 종류·결과(카드 만듦/못 찾음/잠김)만 남기고, 분장표 행 ID·공지 ID·슬롯 값은 남기지 않아요(R11). MCP 호출은 가명 ID·시각·도구 이름·결과(후보 있음/없음/거부)·클라이언트 ID만 남기고, 검색어·조건 값은 남기지 않아요(M5).
  - 알림(R12, 다음 2주로 미룸 · M6): 설계는 그대로 둬요. 가명 ID는 거꾸로 사람을 못 찾아서 알림 주소 표(가명 ID ↔ 알림 주소)를 따로 두고 알림 기능의 DB 역할만 읽어요. 대상은 주문에 들어간 묶음에 표를 준 사람 모두(올린 사람 포함), 링크엔 카드 ID만, 열린 횟수는 셈으로만 남겨요.
  - DB 접근: 운영자도 투표 표·알림 주소 표·승인 표의 갱신 토큰 해시를 직접 읽지 않아요(읽기 역할 분리). 화면과 API는 표 수만 보여 줘요.
  - 운영 표(S 번호 없음): 감사 로그, 10명 이상 묶음 통계, 오류, 모듈별 AI 비용이에요.
- 고려한 대안: 모듈마다 직접 호출 → 등급 검사와 모델 고정이 흩어져요. / 대화형 비서(기억 유지) → 담당 질문이 다른 모듈 호출에 섞여요.
- 결과 · 좋은 점: 원문이 머무는 곳이 `/ask` 서버 메모리 하나예요. 시험으로 0건을 확인할 수 있어요.
- 결과 · 감수할 점: 여러 턴 대화는 못 해요. 원문이 없어 오류를 다시 재현하기 어려워요.
- 결과 · 다시 볼 조건: 사내 모델로 바꾸거나 계약이 바뀌면 모델 허용 목록을 다시 정해요.

### ADR-11 브라우저 공통 입력 검사
- 상태: 채택 · 날짜: 2026-10-23 · 관련: D3, D7, R13, S1, S3
- 맥락: IT 캡처를 뺀 대신 사용자가 오류 문장을 그대로 붙여 넣을 수 있어요. 키·토큰·이메일·IP가 서버에 닿기 전에 멈춰야 해요.
- 결정
  - 검사 대상: 묻기 입력창과 같이 채워요 요청 쓰기 칸 둘 다예요.
  - 잠금: 주민등록번호 형식, 비밀번호 값, 키·토큰 형식(AKIA…, ghp_…, xox…, `eyJ…`, 긴 무작위 문자열), 건강 정보(진단명·알레르기 사전). 이유를 보여 주고, 지우기 전엔 보내기 버튼이 잠겨요.
  - 가림: 이메일·IP를 `[이메일]`·`[IP]`로 바꾼 뒤 보내요. 풀기는 없어요. 입력 칸(S1·S3) 바로 아래 "가림 줄"로 무엇을 가렸는지 보여 줘요.
  - 입력창은 브라우저 자동 완성을 꺼요. 원문은 페이지 메모리에만 두고 브라우저 저장소에 넣지 않아요(R13).
  - 규칙 파일 하나를 브라우저와 서버가 같이 써요(버전 번호 포함). 서버는 같은 규칙으로 다시 검사하고, 걸리면 내용 없이 버리고 감사 로그에 "차단"만 남겨요.
  - 진단명 사전에는 제도 이름(병가 등)을 넣지 않아요.
- 고려한 대안: 서버에서만 검사 → 원문이 이미 서버에 닿아요. / LLM으로 민감 정보 판정 → 판정하려면 원문을 보내야 해요.
- 결과 · 좋은 점: 비용이 거의 없고, 다음 2주의 오류 문장 붙여넣기·캡처 가림이 같은 규칙을 이어 써요.
- 결과 · 감수할 점: 정규식과 사전은 새는 곳이 있어요. "안전해요"라고 말하지 않고 가린 사실만 보여 줘요.
- 결과 · 다시 볼 조건: 정상 질문이 막히는 일이 잦으면 사전을 줄이고, 그 결정은 보안팀과 해요.

### ADR-12 모듈 끄기 스위치
- 상태: 채택 · 날짜: 2026-10-23 · 관련: D1, D6, D13, R4, R9, M5, M6
- 맥락: 그룹웨어 AI를 이미 쓰는 회사라면 회의실·공지는 겹쳐요. 시간이 모자라면 자를 곳도 정해져 있어요(D13). 코드를 고치지 않고 낮출 수 있어야 해요.
- 결정
  - 값(R4): 모듈마다 `켬 | 링크만 | 끔`이에요. `링크만`은 그 종류로 분류되면 S2에 "이 일은 그룹웨어에서 해요" 링크 카드가 떠요. `끔`은 라우터가 그 종류를 후보에서 빼고, 분류되면 담당 안내로 보내요. 예시 칩과 진입점도 숨겨요.
  - 세부 스위치: 회의실 쓰기(켬·끔, 끄면 회의실 카드 주 버튼과 MCP 링크가 그룹웨어 링크), 공지 요약(켬·끔, 끄면 찾기와 원문 링크만), S5(전체·목록만, 목록만 = 묶음 목록 + 분장표 파일 다시 올리기). 이번 2주 기본값은 공지 요약 끔, S5 목록만이에요(M6).
  - MCP 전체 스위치 `켬 | 끔`(M5): MCP 도구는 해당 모듈이 `켬`일 때만 목록에 나와요(`링크만`·`끔`이면 빠짐). 둘 다 빠지면 동의 시트 대신 "지금 연결할 수 있는 도구가 없어요"예요. 실제 어댑터인데 허용 목록이 비어 있으면 MCP는 켜지지 않아요(ADR-15).
  - "같이 채워요 단독" 모드 = navi·notices·rooms 모두 `끔`이에요. 묻기 탭을 숨기고 같이 채워요 탭이 첫 화면이에요. navi `끔`은 이 모드에서만 써요(담당 안내가 다른 모듈의 출구라서요).
  - 레지스트리는 꺼진 모듈 도구를 허용 목록에서 빼요. 실행기는 꺼진 모듈의 plan을 막힘(`기능 꺼짐`)으로 끝내요.
  - 운영 설정에는 설정값도 같이 둬요: 기본 회의 길이, 제안 토큰·plan 만료 시간, 요청 횟수 상한, 세션 재확인 간격. 화면이 아니라 운영 설정이고, 운영자만 바꾸고, 바꿀 때마다 감사 로그에 남겨요.
  - 판정 규칙(D1): 그룹웨어 AI를 켰거나 회의실 실제 연결이 안 되면 회의실·공지를 `링크만`으로 해요. 파일럿에서 회의실이 거의 안 쓰이면 다음 2주에 `링크만`이에요. 운영 주인이 기능마다 다르면 pantry만 남겨요.
- 고려한 대안: 배포 설정으로 기능 빼기 → 되돌리려면 다시 배포해야 해요. / 스위치 없이 처음부터 F3만 → 앞문 가치(D1)를 시험할 기회가 없어요.
- 결과 · 좋은 점: 반대 결론(같이 채워요 단독)으로 바로 낮출 수 있어요.
- 결과 · 감수할 점: 켬·끔 조합마다 시험이 늘어요.
- 결과 · 다시 볼 조건: 파일럿 측정(모듈별 사용)이 나오면 기본값을 다시 정해요.

### ADR-13 세션·퇴사 차단·요청 횟수
- 상태: 채택 · 날짜: 2026-10-23 · 관련: 공통 바닥, R17, M2, M5, F1~F3, S6
- 맥락: 퇴사하면 늦어도 10분 안에 끊겨야 해요(브리프). 토큰은 브라우저에 두지 않아요. 묻기는 부를 때마다 AI 비용이 들고, 게시·+1이 몰리면 판이 어지러워져요.
- 결정
  - 세션: 서버 세션 저장소 + httpOnly·Secure·SameSite 쿠키예요. IdP 토큰은 서버에만 둬요. 쓰기 요청은 CSRF 토큰도 확인해요. 세션 최대 수명은 8시간이에요.
  - 재직 재확인: 세션마다 마지막 확인 시각을 둬요. 재확인 간격(운영 설정, 10분보다 짧게)이 지난 뒤 오는 요청에서 IdP에 다시 확인해요. 재직이 아니면 그 사용자 세션을 모두 지우고 거부해요. IdP가 로그아웃 알림(백채널 로그아웃)을 보내 주면 받아서 바로 지워요(사내 IdP의 지원 여부와 재확인 방법은 확인 필요).
  - "모든 기기 로그아웃"(S6)과 퇴사 확인은 그 가명 ID의 세션과 MCP 승인(갱신 토큰)을 모두 지워요(ADR-15). 세션에는 "누구인지"만 담고, 역할은 요청마다 다시 계산해요(ADR-05).
  - 요청 횟수: 가명 ID × 동작(묻기·게시·+1·MCP 도구 둘)별 카운터를 서버 메모리에 둬요. 시간 창과 상한은 운영 설정이에요. 넘으면 429와 "요청이 많아요. 잠시 뒤에 다시 해 주세요"예요. 카운터에는 횟수만 있어요.
- 고려한 대안: 브라우저에 토큰 → 빼앗기면 퇴사 뒤에도 써요. / IdP 확인 없이 세션 수명만 → 8시간 동안 퇴사자가 남아요. / 횟수를 DB에 → `/ask`가 DB에 쓰게 돼요(ADR-04).
- 결과 · 좋은 점: 퇴사자는 재확인 간격 뒤 첫 요청에서 끊겨요. 세션이 서버에만 있어 한 번에 지울 수 있어요.
- 결과 · 감수할 점: 재확인마다 IdP 호출이 생겨요. 서버를 다시 켜면 횟수 카운터가 처음으로 돌아가요.
- 결과 · 다시 볼 조건: 서버를 여러 대로 늘리면 카운터를 공유 저장소로 옮겨요. 사내 IdP가 정해지면 재확인 방법을 그 IdP에 맞춰요.

### ADR-14 읽기 전용 MCP 도구와 앱 확인 링크
- 상태: 채택 · 날짜: 2026-10-23 · 관련: M1, M3, M5, D5, R2, R5, F1, F2, S2
- 맥락: MCP 도구 결과는 그 도구를 부른 AI 클라이언트의 모델로 가요. 회의실 현황·공지는 등급 1이고, 예약은 앱에서 사람이 한 번 확인해야만 돼요(R2).
- 결정
  - `rooms_find_free`: 입력 {날짜, 시작, 길이(분), 인원, 장비[](정해진 목록), 층(선택)}. 출력 {조회 시각, 모의 여부, 후보 최대 3개 {방 ID, 방 이름, 층, 구간, 맞은 조건[], 예약 링크}, 후보가 없으면 가까운 시간 대안 최대 2개}. 예약자·회의 제목·방별 일정 칸은 타입에 없어요(ADR-06 화면용 타입 재사용).
  - `notices_search`: 입력 {검색어(길이 제한)}. 출력 {허용 게시판 공지의 제목, 게시일, 원문 링크} 목록(최대 개수는 운영 설정). 본문·발췌·요약은 없어요.
  - MCP 경로는 LLM을 부르지 않아요. 회의실은 rooms 읽기 함수, 공지는 색인 검색(규칙)만 써요. DB에도 쓰지 않아요(감사 로그와 메모리 카운터만). 들어오는 값은 남의 입력으로 보고 길이 제한·정해진 목록으로 검증해요. 나가는 제목은 길이를 자르고 제어 문자를 지워 JSON 칸으로만 줘요.
  - 앱 확인 링크(M3): 링크엔 서버가 서명한 짧은 수명의 제안 토큰(조건 슬롯·가명 사용자 ID·만료)만 넣어요. 원문·접근 토큰은 없어요.
  - 링크를 열면 앱 로그인 → 토큰 주인 = 로그인한 사람인지 검사(다르면 열지 않음) → S2 머리 "Claude에서 가져온 후보예요" + 앱이 지금 다시 조회한 카드예요. **링크를 연 건 확인이 아니에요.** [이 방으로 예약] → 확인 시트 [예약하기]가 유일한 확인이에요(ADR-03). 그사이 방이 찼으면 R5 안내 카드 + 대안이에요. 토큰이 만료됐으면 서명이 맞을 때 조건만 꺼내 다시 찾아요. 회의실 쓰기가 꺼져 있으면 링크는 "그룹웨어에서 예약하기"예요.
- 고려한 대안: 공지 본문·인용 요약까지 줌 → 등급 1 본문과 주입 문장이 외부 모델로 가요. / 링크에 조건을 서명 없이 그대로 → 남의 링크로도 열리고 값이 바뀌어도 몰라요. / MCP 예약 도구 + 클라이언트 쪽 확인 → 확인이 우리 손을 떠나요.
- 결과 · 좋은 점: 쓰기 도구가 없어서 주입이 와도 바뀌는 게 없어요. MCP 경로엔 우리 AI 비용이 없어요.
- 결과 · 감수할 점: 공지는 제목뿐이라 클라이언트 답이 얕아요. 제안 토큰이 URL에 실려서 짧은 수명과 주인 검사에 기대요.
- 결과 · 다시 볼 조건: 무보관 계약이 확인되고 보안팀이 허락하면 공지 인용 요약을 MCP에도 줄지 다시 봐요.

### ADR-15 MCP 인가 서버와 허용 클라이언트
- 상태: 채택 · 날짜: 2026-10-23 · 관련: M2, M4, M5, M7, R6, ADR-13, S6
- 맥락: MCP 인가 사양은 보호된 MCP 서버를 OAuth 2.1 자원 서버로 보고, 보호 자원 메타데이터·resource 매개변수·토큰 대상 검사를 요구해요. 결과가 클라이언트 모델로 가니 어느 클라이언트를 받을지도 정해야 해요.
- 결정
  - 역할: `/mcp` = 자원 서버, 우리 서버 = 인가 서버예요. 사용자 로그인은 사내 IdP로 중개해요(ADR-13 세션 재사용).
  - 자원 서버: 토큰이 없으면 401 + `WWW-Authenticate: Bearer resource_metadata=…`예요. 보호 자원 메타데이터(RFC 9728)는 `resource` = MCP 주소 그대로, `authorization_servers` = 우리 발급자 하나, `scopes_supported` = `rooms.read notices.read`예요. 요청마다 `aud`·만료·범위·폐기를 검사하고, 다른 토큰은 받지도 넘기지도 않아요. 범위가 모자라면 403 `insufficient_scope`예요.
  - 인가 서버: 메타데이터(RFC 8414)에 `code_challenge_methods_supported: ["S256"]`를 둬요. 동적 등록 엔드포인트는 없고 CIMD도 광고하지 않아요. 미리 등록한 기밀 클라이언트(ID·비밀·정확한 리디렉트 URI)만 받아요. token 요청엔 PKCE S256과 `resource`가 꼭 있어야 해요.
  - 토큰: 접근 토큰은 짧게(운영 설정, 재확인 간격 이하) 줘요. 갱신 토큰은 쓸 때마다 바꾸고, 갱신 때마다 재직을 다시 확인해요. 재확인 간격 안에선 결과를 재사용해요(Claude는 갱신 응답을 30초까지만 기다려요).
  - 승인 표: (가명 ID, 클라이언트 ID, 범위, 연결한 날, 갱신 토큰 해시). S6 "연결된 AI 앱"(앱 이름·연결한 날·[끊기])이 이 표를 보여 줘요. [끊기]·모든 기기 로그아웃·퇴사 확인은 승인을 바로 폐기해요. "마지막 사용"은 남기지 않아요(M4).
  - 동의 시트: 사내 IdP 로그인 뒤 S6 위에 우리 서버가 띄워요. 앱 이름, 리디렉트 호스트, 읽는 것, 못 하는 것(예약·취소·게시), "찾은 결과는 그 앱의 AI 모델로 보내져요"를 보여 줘요. 허용 목록 밖이면 "회사가 허락하지 않은 앱이라 연결할 수 없어요"만 보여요.
  - 허용 두 겹(M2): 기술로는 등록된 클라이언트 ID·비밀을 가진 조직만 붙어요. 2주 시험 클라이언트는 claude.ai 조직 커넥터 하나이고, 비밀은 조직 소유자만 넣어요. 정책으로는 보안팀 승인 목록(회사 명의 무보관 조건)에 오른 클라이언트만 등록해요. 서버는 계약 여부를 볼 수 없어요. 계약 확인 전엔 허용 목록이 비어 있어서, 실제 어댑터로는 MCP를 켜지 않고 시연은 모의(등급 0) 데이터로만 해요.
  - 네트워크: claude.ai는 Anthropic 송신 대역(`160.79.104.0/21`)에서 붙고, 인가 서버 탐색도 같은 대역에서 와요. 접속 관문에서 `/mcp`·인가 경로만 그 대역에 열어요(보안팀 승인 필요).
- 고려한 대안: 사내 IdP를 그대로 인가 서버로 → 대상 지정·클라이언트 제한 지원을 모르고, 갱신 때 재직 재확인을 못 끼워요(다음 단계 후보). / 동적 등록·CIMD 받기 → 개인 계정 claude.ai도 붙을 수 있어요. / Claude Code·Copilot Studio도 허용 → 비밀이 PC마다 퍼지거나, 네트워크 출발지·보관 조건을 확인하지 못했어요.
- 결과 · 좋은 점: 허용 목록·토큰 수명·재직 재확인을 우리가 쥐어요. 퇴사자는 늦어도 다음 갱신에서 끊겨요.
- 결과 · 감수할 점: 인가 엔드포인트를 직접 만들어요(MCP 3일 중 1.5일). 계약 여부는 정책에 기대요. 관문에 외부 대역용 구멍이 생겨요.
- 결과 · 다시 볼 조건: 사내 IdP가 resource 매개변수·대상 지정을 지원하면 IdP를 인가 서버로 바꿀지 봐요. 새 클라이언트를 넣기 전에 그 클라이언트의 네트워크 출발지·보관 조건부터 확인해요.

### ADR-16 담당 팀 문의와 앱 안 알림
- 상태: 채택 · 날짜: 2026-10-26 · 관련: D9, R12, R13, ADR-03, ADR-10, ADR-11, ADR-13, F1
- 맥락: 담당 카드로 "어디서 하는지"는 알지만, 결국 메일·메신저를 따로 열어 다시 써야 했어요. 사용자가 담당 찾기에서 문의·사유를 적어 담당자에게 보내고, 받는 쪽이 알림을 받게 해 달라고 정했어요.
- 결정
  - 받는 곳: 사람이 아니라 분장표 행의 **주인 부서**예요(D9: 담당자 이름은 분장표에 없어요). 분장표에서 못 찾은 질문은 총무팀으로 가요. 그 부서 사람이면 누구나 "우리 팀에 온 문의"에서 봐요.
  - 보내기: 담당 카드 [○○에 문의하기] → 양식(문의 내용 1,000자·사유 500자, 브라우저에서 공통 검사) → 확인 시트("업무·받는 곳·내 이름과 부서가 같이 가요·보낸 글은 90일 보관") → [보내기]. 고정 버튼 + 멱등 키(화면이 만든 requestId)라서 두 번 눌러도 한 번만 들어가요(ADR-03).
  - 저장: 확인 시트를 거친 문의 글만 `navi_inquiries`에 저장해요. 묻기(검색) 문장은 여전히 저장하지 않아요(R13). 서버도 공통 검사를 다시 돌려 키·주민번호·비밀번호·건강 정보가 든 글은 거부하고, 이메일·IP는 가린 글로 저장해요(ADR-11). 90일이 지나면 지워요.
  - 보낸 사람: 받는 팀이 답하려면 누구인지 알아야 해서 이름·부서를 같이 저장하고 받은 문의함에 보여요. 확인 시트에서 미리 알려요. 다른 부서는 볼 수 없어요.
  - 처리: 받은 부서 사람이 [확인했어요]·[처리했어요]를 누르면(새 문의 → 확인함 → 처리함) 보낸 사람에게 알림이 가요. 답장 글은 이번에 두지 않아요.
  - 알림: 앱 안 알림(`notifications`)이에요. 받는 쪽은 한 사람(가명 ID) 또는 한 부서이고, 읽음은 사람마다예요. **알림 글에는 문의 내용을 넣지 않고** "인사팀에 새 문의가 왔어요 · 업무 이름"처럼 무슨 일인지와 볼 페이지만 넣어요(R12와 같은 뜻). 화면은 15초마다 새로 불러 종에 숫자를 띄우고, 새 알림이 오면 토스트를 보여 줘요. 30일 지나면 지워요.
  - 메일·메신저로 보내는 알림, 밀어 주기(웹 푸시)는 이번에 하지 않아요. 바깥 서비스 연결과 그 서비스의 보관 조건 확인이 먼저예요.
  - LLM은 부르지 않아요. 감사 로그에는 `inquiry.send`·`inquiry.seen`·`inquiry.done`과 결과만 남고 글은 없어요.
- 고려한 대안: 담당자 개인에게 보내기 → 분장표에 사람 이름이 없고(D9), 사람이 바뀌면 문의가 길을 잃어요. / 메일로 바로 보내기 → 바깥 서비스·보관 조건 확인 전이라 이번엔 앱 안에서만 해요. / 익명으로 보내기 → 받는 팀이 답할 수 없어요.
- 결과 · 좋은 점: 담당 찾기에서 끝까지 끝낼 수 있어요. 받는 팀은 문의가 한곳에 모이고 처리 상태를 남겨요.
- 결과 · 감수할 점: 묻기와 달리 사람이 쓴 글이 DB에 남아요(90일). 부서 전체가 받아서 누가 맡았는지는 상태만으로 알아요. 알림은 앱을 열어야 보여요.
- 결과 · 다시 볼 조건: 부서 안 창구 담당(IdP 그룹)이 생기면 그 사람들만 받게 좁혀요. 메일·메신저 알림을 붙일 때는 알림 글에 내용을 넣지 않는 규칙을 그대로 지켜요.
