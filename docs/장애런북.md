# 장애 런북 — 첫 조치 (2026-10-29)

- 근거: `docs/배포준비회의_2026-10-29.md` C7·F8·쟁점 2·쟁점 5
- 누가 써요: 파일럿 운영자(정보보안팀)와 대리 1명
- 원칙
  - 기능 하나의 문제는 **스위치**로 끄고, 바닥 문제(5xx 급증·흰 화면·로그인 전부 실패)는 **되돌리기**로 풀어요.
  - 직원이 쓴 글·이름·검색어는 기록·알림·대화에 옮기지 않아요. 요청 번호(`x-request-id`)·판(`x-desk-build`)·시각은 적어도 돼요.
  - 서버를 다시 띄우면 모두 로그아웃돼요(세션이 메모리에 있어요, 앞선 회의 F1 전까지). 재시작은 마지막 수단이에요.

## 0. 먼저 볼 것(5분)

1. 관문 안에서 `/health/ready`: `ok`, `db`, `retention`, `build`를 봐요. `retentionFailing`(지금 실패 중인 보관 단계 이름)이 비어 있지 않거나 `retentionStale`(3시간 넘게 다 못 지움)이 `true`면 3번의 `retention-failed`를 먼저 봐요. `/health/live`가 200이면 프로세스는 살아 있어요.
2. 떠 있는 판(`build`)이 마지막으로 배포한 커밋이 맞는지 봐요.
3. 로그 건수(사내 수집기, 지난 15분)
   - `server-error`: 서버 오류
   - `retention-failed`: 7일 보관 지우기 실패(`step`에 단계 이름, `times`에 연달아 실패한 횟수)
   - `retention-stuck`: 같은 단계가 3번 연달아 실패했어요. 이때 운영자 역할에게 앱 알림도 한 번 가요(글에 단계 이름 없음)
   - `db-pool-error`: DB 연결 문제
   - `idp-unreachable`: 회사 로그인에 닿지 못함
   - `idp-no-auth-time`: 회사 IdP가 인증 시각을 주지 않아 로그인을 받지 않음
   - `server-started`: 서버가 다시 뜸(업무 중이면 원인을 찾아요)
   - `db-newer-migrations`: 더 새 판이 붙인 마이그레이션 기록이 있는 채로 앞 판이 떠 있음(3절로 되돌린 상태, 11/11)
4. 마지막 배포 시각과 바꾼 스위치(운영 설정 감사 로그)를 봐요.

## 1. 스위치 바꾸는 법

아직 운영 설정 화면이 없어요(스위치 CLI는 P1). 지금은 둘 중 하나로 바꿔요.

**가. 운영자 계정으로 로그인한 브라우저(우선)**: 개발자 도구 콘솔에서 불러요. 운영자 가명으로 감사 로그에 남고, 서버는 바로 막아요. 이미 열린 화면은 새로 고쳐야 바뀐 스위치를 봐요.

```js
const { csrfToken } = await (await fetch('/api/me')).json();
const put = (path, body) =>
  fetch(path, { method: 'PUT', headers: { 'content-type': 'application/json', 'x-csrf-token': csrfToken }, body: JSON.stringify(body) }).then((r) => r.json());
await put('/api/ops/flag', { flag: 'autoActions', value: false }); // 채팅 바로 실행 끄기
// await put('/api/ops/flag', { flag: 'roomsWrite', value: false }); // 회의실 쓰기 끄기
// await put('/api/ops/flag', { flag: 'mcp', value: false }); // MCP 끄기
// await put('/api/ops/switch', { module: 'rooms', value: 'link' }); // 회의실을 "링크만"으로
// await put('/api/ops/values', { rateLimitPerMinute: 10 }); // 분당 요청 상한 낮추기
```

**나. 운영자가 로그인할 수 없을 때(IdP 장애 등)**: DB에서 바꾸고 서버를 다시 띄워요. 서버는 뜰 때만 이 표를 읽어서, 다시 띄우기 전에는 반영되지 않아요(= 모두 로그아웃). 감사 로그에 남지 않으니 장애 기록에 꼭 적어요.

```sql
-- 운영 설정은 ops_settings(id = 1)의 overrides(jsonb) 한 줄에 있어요.
update ops_settings set overrides = coalesce(overrides, '{}'::jsonb) || '{"autoActions": false}'::jsonb where id = 1;
-- 회의실 쓰기 끄기: '{"roomsWrite": false}' / MCP 끄기: '{"mcp": false}'
```

| MCP(외부 AI 앱)가 이상해요 | `mcp` 끔 | 클라이언트 폐기는 DB에서 해요(ops 스크립트는 P1). 정보보안팀에 알려요 |

| AI 비용이 갑자기 늘어요 | 운영 값 `aiDailyCalls`(회사 전체 하루 AI 호출 상한, 기본 2,000번)를 낮춰요. 0이면 AI를 부르지 않아요 | 운영 표 AI 비용(모듈·목적별 수)을 봐요. 상한에 걸리면 그날은 낱말 규칙으로만 답하고 카드에 "AI 정리"가 없어요. 공급자 콘솔의 지출 한도도 같이 걸어 둬요(11/11 QA Q7) |
| 회사 로그인이 안 돼요(`idp-unreachable`) | 앱에서 할 일은 없어요 | IT 창구에 알리고 사내 공지를 내요. 이미 들어온 사람은 계속 써요 |
| 회사 로그인이 모두 실패해요(`idp-no-auth-time`) | IdP 담당에 `max_age`·`auth_time` 지원을 확인해요 | 급하면 바로 앞 판으로 되돌려요(3절). 회사 IdP 바꾼 날이면 그 설정부터 봐요 |
| DB가 안 돼요(`/health/ready` 503, `db-pool-error`) | 관리형 DB 상태를 봐요 | `/health/live`는 200이라 재시작하지 않아요. 오래가면 사내 공지를 내요 |
| 보관 지우기가 실패해요(`retention-failed`) | 5분 뒤 저절로 다시 돌아요 | 같은 `step`이 계속 실패하면(`retention-stuck`, 운영자 앱 알림) 그날 안에 고쳐요(7일 보관 약속) |
| 배포 직후 5xx가 늘거나 흰 화면이에요 | 3절 기준에 걸리면 되돌려요 | 원인을 찾은 뒤 다시 배포해요 |
| 응답·로그·관문 로그에 직원 글이 보여요(카나리) | **바로 되돌려요** | 정보보안팀에 바로 알려요. 보인 곳·기간만 적고 글은 옮기지 않아요 |
| 업무 중에 서버가 다시 떴어요(`server-started`) | 원인을 찾아요(메모리·노드 이동) | 한 주에 한 번을 넘으면 세션 표(앞선 F1)를 당겨요(쟁점 2) |
| 시연이 더럽혀졌어요(이상한 글·스위치) | 시연 컨테이너를 다시 띄워요(tmpfs라 처음으로 돌아가요) | 명단 밖으로 넓힌 시연이면 `DESK_DEMO_WIDE=true`로 띄워요(문의 저장·운영 설정 바꾸기를 막아요) |

## 3. 되돌리기

- 기준(배포 뒤 30분, 수치는 회사가 확인해요)
  - `/health/ready` 503이 2분 이어져요.
  - 5xx가 5분에 10건을 넘거나 1%를 넘어요.
  - IdP는 정상인데 로그인 실패가 10분에 5건을 넘어요.
  - 지원 브라우저에서 흰 화면이에요.
  - 직원 글·내용이 응답·로그에 보여요 → 기준과 상관없이 바로예요.
- 방법
  1. 바로 앞 이미지 태그(커밋)로 같은 환경 값을 넣어 다시 띄워요(`--stop-timeout 50`). Fly는 `flyctl releases -a <앱>`으로 앞 판 이미지를 찾아 `flyctl deploy -i <이미지>`예요.
  2. 마이그레이션은 되돌리지 않아요. 한 배포에서는 넓히기만 해서 앞 판이 그대로 떠요.
     - 새 마이그레이션을 넣은 배포를 되돌리면 DB 기록에 앞 판 폴더에 없는 이름이 남아요. 앞 판 폴더의 파일이 모두 같은 내용으로 적용돼 있으면 서버는 뜨고 `db-newer-migrations` 경고(이름만)를 남겨요. release_command(`db:migrate`)도 할 일이 없다고 끝나요(11/11 QA Q1).
     - 앞 판 폴더의 파일 중 적용 안 된 것이 있거나 적용한 파일 내용이 다르면 그대로 멈춰요(합치기 전 옛 DB·고친 파일). 이때는 되돌리지 말고 리드에게 알려요.
     - 새 판을 다시 올리면 경고는 없어져요. 새 판이 표를 지우거나 칸 이름을 바꾸는 마이그레이션을 넣었으면 앞 판이 깨지니, 그런 변경은 두 번에 나눠 배포해요(넓히기 → 다음 배포에서 좁히기).
  3. `/health/ready` 200과 `build`가 앞 판인지 보고, `node scripts/smoke.mjs <주소>`를 돌려요.
  4. 모두 로그아웃됐다고 사내 공지를 내요.

## 3-1. 백업과 복원(11/11 QA Q3)

> 보관 기간 숫자는 ADR-21 "백업 줄" 결정(11/23까지, 개선회의 10/29 3번)을 따라요. 아래 숫자는 그 회의의 권고안이고, 결정되면 고쳐요.

- 무엇을 남겨요
  - 본 DB: 관리형 PostgreSQL의 **시점 복구(PITR)를 켜요**. 권고는 7일이에요(기록 7일 원칙과 같게). 백업에도 7일 기록이 최대 7일 더 남는다는 것을 S6 안내에 적어요(결정 뒤).
  - 접속기록(`access_log`, 1년, ADR-20): 본 DB 백업과 따로, 한 달에 한 번 내보내 고칠 수 없는 저장소(객체 잠금 1년 이상)에 둬요. 내보낼 때 칸은 표 그대로예요(글·이름 없음).
  - 비밀 값(`tenant.env`)은 저장소 밖 비공개 폴더에만 있어요. 백업과 같은 곳에 두지 않아요.
- 업데이트 전
  1. 배포 창(4절) 시작 전에 관리형 DB 스냅숏을 하나 찍어요(이름에 커밋 앞 7자만, 회사 이름 없음).
  2. 그다음 `npm run tenant -- deploy`(마이그레이션 → 배포 → 연기 시험)예요.
- 복원 순서(DB를 잃었거나 잘못 바뀌었을 때)
  1. 앱을 멈춰요(`flyctl scale count 0 -a <앱>`). 사내 공지를 내요.
  2. 관리형 DB 화면에서 빈 새 DB로 시점 복구를 해요(지금 DB를 덮어쓰지 않아요).
  3. 복원한 DB에 앱 계정 권한을 다시 줘요: `psql "<소유자 주소>" -v app_role=<앱 계정> -f db/roles/app-grants.sql`. 끝나면 `DATABASE_URL=<앱 계정 주소> node --import tsx apps/server/scripts/grant-check.ts`로 권한이 맞는지 봐요(읽기만).
  4. **복원한 DB에 `db:migrate`를 먼저 돌리지 않아요**(고객사DB분리회의 10/31 4번). 백업 때의 판 이미지로 먼저 띄워요. 그 판이 뜨면(빠진 마이그레이션 없음) 그다음 지금 판을 배포해 release_command가 마이그레이션을 이어 적용하게 해요.
  5. `DATABASE_URL`·`DESK_MIGRATE_DATABASE_URL`을 새 DB로 바꾸고(`flyctl secrets set`, 값은 운영자가 자기 터미널에서) 앱을 다시 켜요. `/health/ready`·연기 시험을 봐요. 첫 보관 회차가 끝나기 전에는 `/health`가 503일 수 있어요.
  6. 복원 시점과 잃은 시간(대략)을 장애 기록(5절)에 적어요.
- 연습: 분기에 한 번, 시험 DB로 2~5번을 돌려 봐요.
