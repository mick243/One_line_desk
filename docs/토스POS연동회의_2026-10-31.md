# 사내 카페 주문을 토스 POS로 넣는다면 — 회의 (2026-10-31)

- 참석: 리드(진행·문서 조사), 백엔드·연동 설계, 보안·개인정보, 기획·사업제휴 겸 운영. 모두 에이전트예요. 코드는 고치지 않았어요.
- 안건: 사내 카페테리아 주문 기능(가칭 `cafeteria` 모듈)을 만들고 카페 POS가 토스 POS라고 가정할 때, 토스플레이스의 "별도 승인"과 공통 가이드가 무엇을 요구하고 우리 설계·일정에 어떤 영향을 주는지.
- 상태: **검토만 했어요.** 카페 주문은 지금 PRD 범위 밖이에요("실제 구매 주문, 결재·업체 연동", `docs/PRD.md`). 만들려면 사용자 결정과 새 ADR이 먼저예요.
- 토스플레이스 사실은 2026-10-31 공식 문서 조사예요(아래 출처). 문서에 없는 것은 "확인할 것"에 모았어요.

## 1. 토스플레이스 공식 문서 사실

**누가·어떻게 쓰나**
- Open API는 "솔루션 파트너사를 위한 서비스"예요. 서버↔서버 연동이고, 매장(가맹점)이 우리 앱을 설치해야 그 매장 `merchantId`로 호출할 수 있어요.
- 시작: 개발자센터 가입(이메일 인증) → 앱 등록(타입 API, 이름·앱 ID·회사명) → Access Key·Access Secret 발급(Secret은 만들 때 한 번만 보이고, 잃으면 지우고 새로 만들어요) → 테스트 가맹점 연결(매장고유번호·사업자번호·휴대폰) → 개발.
- 운영 전환: 테스트 배포(테스트 단말만) → 라이브 배포 검수 요청 → 검수 뒤 서비스 코드를 카페에 전달 → 카페가 토스 POS 설정 > 기타설정 > 서비스 연동 > 서비스 코드로 연결에서 직접 설치. 토스 POS가 없는 매장은 VAN 대리점을 통해 적용해요.
- 테스트 가맹점 결제 단말에서 결제하면 **실제 승인**이 나요.

**별도 승인**
- 주문 생성은 "추후 공지가 있을 때까지 승인을 받은 앱에서만" 쓸 수 있어요. 주문 상태 변경(수락·거절·취소)도 승인 앱만, Open API로 만든 주문에만 돼요.
- 신청: 개발자센터 지원 메일(developer-support@tossplace.com)로 앱 이름·설치 매장 정보·사용 목적 등을 보내요.
- 심사 기준·기간·요금·계약 형태는 문서에 없어요.

**공통 가이드**
- 인증: 요청마다 헤더 `x-access-key`, `x-secret-key`(요청 서명 없음, 범위·IP 허용 목록 언급 없음). Base `https://open-api.tossplace.com/api-public/openapi/v1`, Swagger 있음.
- 호출 제한: 매장별 토큰 버킷, 초당 10개 충전·최대 100개, 넘으면 429, `x-ratelimit-limit/remaining/reset`(epoch ms).
- 응답: `resultType` SUCCESS/FAIL, 실패는 `error{errorCode, reason, data}`. 모든 응답에 `x-toss-event-id`(문의용). 시각은 ISO 8601. ALPHA 기능은 예고 없이 바뀔 수 있어요.

**주문**
- `POST /merchants/{merchantId}/order/orders`. `orderKey`(≤128, 중복이면 거부 → 사실상 멱등 키), `orderNumber`(≤64, 매장 주문번호, 문서는 "일련번호나 고객명" 권장), `lineItems`(카탈로그 상품 ID·가격·수량·옵션), `chargePrice`(호출 측 계산, 내역과 안 맞아도 거부 안 됨), `payments` 필수(모두 "외부결제수단"으로 기록).
- 상태: `requestedInfo`가 있으면 REQUESTED(POS에서 수락하면 주문서 자동 출력), 없으면 OPENED, 결제가 끝났으면 COMPLETED. 주문 취소는 결제를 취소하지 않아요.
- 거부: 중복 `orderKey`, 카탈로그에 없는 상품·옵션, 품절, 옵션 개수 위반.
- POS 표시: 매장 업종이 카페·음식점이고, POS가 켜져 있고, [현황] > [주문표시]에서 우리 앱이 선택돼 있어야 해요. 당일 주문만 보여요.

**웹훅**
- `x-toss-signature: v1=<hex HMAC-SHA256(secret, "<x-toss-timestamp>.<rawBody>")>`. 타임스탬프 차이가 큰 요청은 거부를 권해요(창은 미지정). 실패하면 재시도하고, 계속 실패하면 전송을 멈출 수 있어요. 최소 한 번 전달이라 `x-toss-webhook-id`로 중복을 걸러요. 여러 매장이 한 엔드포인트로 오고 payload `merchantId`로 나눠요.

## 2. 한눈에(3명 의견을 합침)

1. **가장 큰 걸림돌은 회사별 분리(ADR-23)예요(3명 모두).** 토스 키·웹훅은 우리 앱 단위라서, 키 하나를 회사마다 같이 쓰면 A사 서버가 B사 카페에 주문을 넣을 수 있고 웹훅을 회사별로 나눠 줄 중계기가 필요해져요. → 토스에 **회사마다 앱·키를 따로 받을 수 있는지**(승인·검수도 회사마다인지) 먼저 물어요. 안 되면 회사마다 허용 `merchantId`를 고정하고 다른 매장은 서버가 거부하며, 웹훅 대신 주문 상태를 조회로만 받아요.
2. **신청 주체는 개발사(솔루션 파트너)예요.** 설치 동의는 카페 사업자(외부 위탁 업체면 그 사장님)가 서비스 코드를 직접 입력하는 거라, 고객사가 대신할 수 없어요. 고객사–개발사–카페 세 당사자 합의가 필요해요.
3. **주문은 확인 시트에서만, 자동 실행 허용 목록(ADR-19)에는 넣지 않아요(3명 모두).** 돈과 매장 일이 걸리고 바깥으로 가요. MCP는 메뉴 조회와 앱 확인 링크만이에요(ADR-14와 같음).
4. **POS로는 메뉴·옵션 코드·수량·서버가 계산한 금액·픽업 번호만 보내요.** 문서가 권하는 `orderNumber` 고객명, `orderer`(ALPHA), 자유 메모는 쓰지 않아요(바깥 서비스 최소 정보, 이름 비노출). 요청사항은 처음엔 정해진 선택지 코드("얼음 적게")로만 받아요. 자유 메모는 plan에 자유 문장을 두지 않는 ADR-03과도 부딪혀요.
5. **결제는 우리 앱이 돈을 받지 않는 쪽이에요.** 1순위는 "매장 수락 뒤 현장 결제"(`requestedInfo`로 REQUESTED)인데, `payments`가 필수라 **빈 값·0원을 받아 주는지 Swagger·토스 확인**이 먼저예요. 안 되면 "회사 후불 정산 + 1인 하루 한도"(외부결제수단 합계로 카페가 회사에 청구)예요. 식대 차감은 급여 자료(등급 2)·장기 보관이 생겨서 미뤄요.
6. **일정: 파일럿 1단계(동결 11/30)에는 넣지 않아요.** 승인 기간을 몰라서 신청은 일찍(고객사·카페 동의를 받은 뒤) 하고, 그동안 모의 POS로 개발해요. 빨라도 2단계에 "모의 POS 또는 링크만", 실매장은 승인·검수 뒤 따로 켜요.

## 3. 설계 요점(만든다면)

- **어댑터**: `PosAdapter { menu, placeOrder, status, cancel }`, 구현은 `MockPos`(가상 메뉴·품절·중복 거부·수락 흉내, 시연 띠) · `HttpPos`(가상 토스 서버에 붙는 계약 시험용) · `TossPos` · `OffPos`(연결 안 함). 운영에서 모의를 막는 목록에 넣어요.
- **멱등**: 서버가 UUID `order_key`를 만들어 주문 행에 적고 그 값을 `orderKey`로 보내요. 다시 보낼 때도 같은 키예요. 가명 ID·우리 영수증 키는 토스로 나가지 않아요.
- **실행 순서**: 지금 고정 실행기는 트랜잭션 안에서 실행해요. POS 호출을 그 안에 넣으면 긴 트랜잭션이 생기고 PGlite에서는 멈출 수 있어요. 회의 초대처럼 **DB에 `sending` + `order_key`를 먼저 적고, 트랜잭션이 끝난 뒤 POS를 불러요.** 결과를 모르면(시간 초과·5xx) `unknown`으로 두고 정리 작업이 같은 키로 다시 보내요(중복 거부가 오면 이미 만들어진 것).
- **금액**: plan에는 메뉴 ID·옵션·수량만 두고, 실행 순간 카탈로그 가격으로 서버가 다시 계산해요. 시트에 보인 금액과 다르면 막힘으로 끝내고 다시 확인받아요(토스는 금액 불일치를 거부하지 않아서요).
- **메뉴**: 서버 메모리 캐시 5분(운영 값으로 조절), 확인 시트를 열 때 다시 받아 품절·가격 확인, 품절 거부가 오면 캐시를 버려요. 영업시간은 운영 설정에 둬요(토스 API에 없음).
- **웹훅(쓸 수 있을 때만)**: `/api` 밖 별도 경로(예 `/hooks/toss/v1`), 세션 없음, 원문 문자열로 받아 서명을 상수 시간 비교, 타임스탬프 ±5분, `merchantId`가 이 회사 값인지 확인, `x-toss-webhook-id` 중복 표(7일), 원문 본문은 보관하지 않아요. 관문 허용 목록에 이 경로 하나만 더하고(보안팀 승인) 로그 가리기 목록에도 넣어요. 웹훅은 우리 주문 행의 상태만 바꿔요.
- **비밀 값**: `DESK_POS=toss|mock|off`, `TOSS_ACCESS_KEY`·`TOSS_SECRET_KEY`·`TOSS_MERCHANT_ID`·`TOSS_WEBHOOK_SECRET`. 회사별 `tenant.env`에만, 기본은 `DESK_POS=off`(카페를 쓰지 않는 회사의 검사가 막히지 않게). 운영 검사: 모두 있거나 모두 없음, 개발용 값 거부, 웹훅 Secret ≠ API Secret, 시연 배포에 실제 키 금지. 키 머리는 로그·오류에 남지 않게 하고 카나리 시험으로 지켜요. 사내 나가는 프록시가 TLS를 풀어 머리를 기록하지 않는지 네트워크팀에 확인해요.
- **새 표(7일)**: `cafeteria_orders`(order_key·픽업 번호·상태·금액·pos 주문 ID·event id), `cafeteria_webhook_seen`. 감사 로그는 정해진 칸만(module `cafeteria`, action `order`, 결과 코드).
- **운영 스위치(ADR-12)**: 카페 모듈 켬·링크만·끔, 주문 쓰기 켬·끔(운영 기본 끔), 주문 받기 일시 중지, 영업시간·마감, 1인 하루 한도, 허용 `merchantId`. POS가 꺼져 주문이 안 보이는 일에 대비해 N분 안에 수락이 없으면 직원에게 알리고 [주문 취소]를 주고, 주문서 프린터를 켜고, 개점 점검표에 "POS 실행·주문표시에 앱 선택"을 넣어요.
- **고칠 곳(대략)**: `packages/shared/src/kinds.ts`(새 종류 → CLAUDE.md 종류 목록·ADR), `core/tool-registry.ts`(`cafeteria_menu` 읽기), MCP 범위 `cafeteria.read`, `adapters/*`, `modules/cafeteria/`, `core/rate-limit.ts`, `config.ts`, `scripts/tenant-lib.ts`.

## 4. 승인 신청서 "사용 목적" 초안

> 저희는 기업 고객사 사내 직원 전용 업무 앱("한 줄 데스크")을 운영하는 솔루션 개발사이고, 고객사 사옥 안 카페(토스 POS 사용 매장)에서 직원이 앱으로 주문하면 그 주문을 매장 POS 주문 현황에 넣으려고 해요. 주문은 직원이 앱 확인 화면에서 직접 누른 경우에만 서버가 만들고, 금액은 서버가 매장 메뉴 가격으로 계산해요. 주문에는 메뉴·옵션·수량·금액·픽업 번호만 담고 이름·연락처 같은 개인정보는 보내지 않아요. 결제는 [매장 수락 뒤 현장 결제 / 고객사 월 후불 정산] 방식이에요. 직원 약 150명 사옥 기준 점심 피크(약 30분)에 주문 40~60건을 예상하고, 서버에서 줄을 세워 매장별 초당 5건 이하로 호출해요. 인증 키는 서버 비밀 저장소에만 두고 로그에 남기지 않아요. 매장 1곳부터 시작해 사용 결과를 보고 넓힐 계획이에요.

- 설치 매장 정보를 적으면 고객사 관계가 드러나요. 회사 ID와 회사 이름의 대응을 비공개로 두는 원칙(ADR-23)에 맞게, 신청 메일과 답신은 저장소 밖에 둬요.

| 11 | 라이브 검수 기준·기간, 업데이트 때 재검수 여부, SLA·장애 연락처, ALPHA 변경 공지 | 운영 |
| 12 | 테스트 가맹점에서 단말 결제 없이 외부결제로만 시험할 수 있나, 설치 해제·위탁 업체 교체 절차 | 시험·운영 |

## 6. 결정할 것

| 누가 | 무엇을 |
|---|---|
| 사용자 | 카페 모듈을 범위에 넣을지와 단계(1단계 제외 권고), 회사별 앱 vs 앱 하나 + 허용 매장 고정, 정산 대사를 어떻게 할지(앱 기록은 7일), 카페 사장님에게 일시 중지 권한을 줄지 |
| 고객사 | 결제·정산 방식, 1인 한도, 위탁 카페와의 합의, 처리방침 고지(카페 POS로 메뉴·금액·주문번호가 감) |
| 위탁 카페 | 서비스 코드 설치 동의, POS 설정과 개점 점검, 영업시간, 취소 응대 |
| 토스플레이스 | 5절 답변(특히 2·3·4·5번이 구조를 정해요) |

**승인이 거절되면**: 주문서만 카페 태블릿·프린터로 보내기(카페가 POS에 다시 입력), POS가 다른 카페면 어댑터만 바꾸기, 또는 운영 스위치 `링크만`.
