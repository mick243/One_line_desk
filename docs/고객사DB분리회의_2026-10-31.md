# 고객사가 개발사 없이 DB를 사내로 바꿀 수 있나 — 회의 (2026-10-31)

> **상태: 보류(2026-10-31 사용자 결정).** 온프레미스 이관 준비물(5절)과 코드 확인 거리(6절)는 진행하지 않아요. 실제 고객사 요청이 오면 다시 열어요.

- 참석: 리드(진행), A사 정보보안팀(가상 고객사 역할), 백엔드·DB, 배포·운영 겸 계약·개인정보. 모두 에이전트예요. 코드는 고치지 않았어요.
- 안건: 가상의 고객사 A사 보안팀이 개발사 DB에 A사 자료가 쌓이는 걸 문제 삼아, "사내 IP를 이용해 지금 DB를 떼어 내고 A사 사내 PostgreSQL을 붙이겠다. 개발사 개입 없이 하겠다"고 해요. 이게 현실적으로 되는지 판정해요.
- 기준: ADR-01·20·21·23·24, `docs/회사추가절차.md`, `docs/배포준비회의_2026-10-29.md`, `apps/server/src/config.ts`, `core/db/`, `db/migrations/`, `apps/server/scripts/tenant*.ts`
- 법 조문·Fly 기능 설명은 참석자의 일반 지식이에요. 계약 전에 원문으로 다시 확인해요.

## 한눈에

1. **지금 구조로는 개발사 없이 안 돼요(3명 모두).**
   - DB 연결은 `DATABASE_URL` 하나이고, 이 값은 개발사 Fly 계정의 그 회사 앱 비밀 값이에요. A사가 바꿀 길이 없어요(운영은 `.env`도 읽지 않아요).
   - A사가 어떻게든 바꿔도 개발사가 다음 배포 때 비공개 폴더의 `tenant.env`로 다시 덮어써요(`tenant.ts`의 `secrets import`).
   - 개발사 클라우드 앱을 A사 사내 DB에 잇는 일(VPN·고정 출구 IP)도 개발사 계정 작업이에요.
2. **"DB만 사내로"는 보안 이득이 거의 없어요(A사 보안팀).** 개발사 앱이 DB 계정을 쥐고 모든 행을 읽고 쓰고, 글도 개발사 서버 메모리를 지나가요. 쌓이는 위치만 바뀌어요. 게다가 사내 DB를 국외(도쿄) 클라우드에 열어야 하고 지연·끊김·국외 이전이 남아요.
3. **현실적인 길은 앱 서버까지 A사 사내에 두는 온프레미스예요(3명 모두).** 앱 코드는 고칠 필요가 없어요(회사별 한 벌·이미지 하나 구조 덕분이에요). 개발사가 **한 번** 이관해 주면 그 뒤 비밀 값·IdP·DB·마이그레이션·업데이트 적용·접속 통제는 A사 혼자 해요. 개발사는 서명 이미지와 2차 지원만 해요.
4. **개발사 없이 하면 되돌릴 수 없게 깨지는 곳이 있어요.** `PSEUDONYM_SECRET`을 새로 만들면 기존 예약·문의·1년 접속기록이 사람과 끊겨요. 판이 다른 이미지나 마이그레이션 누락은 시작 검사가 일부러 멈춰 세워요.

## 1. 개발사 없이 되는 것·안 되는 것

| 하고 싶은 것 | 개발사 없이? | 이유 |
|---|---|---|
| 사내 PostgreSQL 17 만들기, `btree_gist`, 계정 나누기, TLS, 백업, 방화벽 | 돼요 | 코드가 막지 않아요. 확장은 `btree_gist` 하나뿐이에요(pgcrypto 필요 없음) |
| 앱 계정 권한(GRANT) 주기 | 반쯤 | 마이그레이션에 GRANT가 없어서 표마다 어떤 권한이 필요한지 개발사 답이 필요해요 |
| 개발사 운영 앱의 `DATABASE_URL` 바꾸기 | 안 돼요 | 개발사 Fly 계정 비밀 값이고, 배포 때마다 개발사 `tenant.env`로 덮어써져요 |
| 개발사 운영 앱 ↔ 사내 DB 잇기(VPN·출구 IP) | 안 돼요 | Fly 쪽 설정은 개발사 계정 작업이에요 |
| Fly 권한을 A사에 나눠 주기 | 받아들일 수 없어요 | 조직 권한은 다른 고객사 앱의 비밀 값과 앱 이름(= 고객 목록)까지 보일 수 있어요(ADR-23 위반) |
| 기존 자료 옮기기 | 안 돼요 | A사에는 개발사 DB·백업 접근이 없고, 저장소에 내보내기 도구도 없어요 |
| 개발사 쪽 접속기록 지금 바로 지우기 | 안 돼요(법으로도) | 법정 1년이고 DB 트리거가 1년 안 줄의 삭제를 막아요. "지운다"가 아니라 "A사로 넘겨 1년을 채운다"예요 |
| 온프레미스로 처음 띄운 뒤 운영 | 돼요 | 이미지와 업데이트 판을 받을 권리만 있으면 돼요 |

## 2. 배포 모델 비교

| 항목 | ① 개발사 운영(지금) | ② 개발사 앱 + A사 사내 DB | ③ A사 온프레미스 |
|---|---|---|---|
| A사 혼자 하는 것 | 앱 안 운영 스위치뿐 | DB 백업·계정·네트워크 | 거의 전부 |
| 개발사가 필요할 때 | 처음·업데이트·장애 모두 | 처음·업데이트·장애 + VPN | 이관 한 번, 이미지 릴리스, 2차 지원 |
| 보안 | 회사끼리 섞이지 않음. 자료가 개발사·Fly(국외)에 | 사내 DB를 국외 클라우드에 열어야 해서 공격 면이 가장 넓음. 개발사가 여전히 모든 자료에 닿음 | 자료·비밀 값이 A사 안에만. A사 운영 역량에 기댐 |
| 지연·안정 | 낮음 | 질의마다 도쿄↔한국 왕복, VPN이 흔들리면 ready 503, 재시도 없음 | 가장 낮음 |
| 개인정보 | 처리 위탁(Fly 재위탁) | 여전히 위탁, 국외 이전도 남음 | A사가 직접 처리. 국외 이전 없어짐(AI를 켜지 않는 한) |
| 권고 | 기본 | **권하지 않음** | A사가 단독 운영을 원하면 이 안 |

A사 보안팀이 원하는 게 "자료를 국내에 두기"뿐이라면 ①을 국내 리전으로 운영하는 안도 같이 보여 줘요.

## 3. 온프레미스 이관 순서(개발사가 한 번 해 줌)

1. 작업 창을 잡고 운영 앱을 쓰기 중지로 바꿔요(장애런북 스위치 또는 관문 점검 화면).
2. `pg_dump -Fc`로 전체 덤프 → 암호화해서 넘기고 해시를 맞춰요. `schema_migrations`(파일 이름·sha256)도 같이 와야 해요.
3. 회사 비밀 값 넷, 특히 **`PSEUDONYM_SECRET`을 그대로** 안전한 경로로 넘겨요. 새로 만들지 않아요. 개발사 쪽 사본은 파기해요.
4. A사가 같은 커밋 이미지(digest 고정)를 받아요. 빈 DB에 `pg_restore --no-owner --no-acl` → GRANT 스크립트 → 점검. **복원한 DB에 `db:migrate`를 먼저 돌리지 않아요**(겹쳐서 깨져요). 복원 대신 새로 시작하면 마이그레이션만 돌리고 접속기록·운영 설정·MCP 연결·앞으로의 예약만 따로 옮겨요(나머지는 7일 기록이라).
5. `DATABASE_URL`(`sslmode=verify-full`, 사내 CA는 `NODE_EXTRA_CA_CERTS`) 등 환경 값을 넣고 한 대로 띄워요 → `/health/ready` → `SMOKE_BUILD=<SHA> node scripts/smoke.mjs <주소>`를 함께 확인해요.
6. A사 IdP에 리디렉트를 다시 등록하고 DNS를 사내로 옮겨요. IdP를 바꿔 `subject`가 달라지면 가명 ID가 끊기니, 같은 IdP 주체를 유지해요.
7. 개발사는 Fly 앱·DB·시점 복구 백업·접속기록 잠금 저장소·로그를 지우고 **파기 확인서**를 내요(지금 절차에 양식이 없어요). 비공개 폴더에서 A사 `tenant.env`를 지워 일괄 배포 대상에서 빼요.

## 4. 계약에 적을 것

- 소스 또는 서명 이미지(커밋 SHA·digest·SBOM)와 업데이트 판을 받을 권리, 보안 수정 제공 기한, 소스 에스크로
- 지원할 판(예: 최신과 바로 앞 판), 소스로 직접 빌드하는 것은 지원하지 않음(판이 `dev`가 되면 안전장치가 꺼져요)
- 책임 경계: 개발사는 이미지 동작·마이그레이션 스크립트·보안 공지·2차 지원 응답, A사는 가용성·비밀 값·접속기록 1년 보관·백업·업데이트 시점
- 면책: 지원 판이 아님, 이미지를 바꿈, 마이그레이션을 빠뜨림, 운영 설정 검사를 우회함
- 이관 전까지 처리 위탁 계약(국내 리전, 재위탁 고지, 개발사 운영 인력 접근 기록·통보), 이관 뒤 위탁 종료 합의와 처리방침 갱신
- 이관 뒤 개발사 원격 접근은 A사 PAM 일시 계정·녹화·접속기록 아래에서만
- AI는 규칙만(`DESK_AI_PROVIDER=fake`) 기본, Slack 끔, 시연 환경과 섞지 않기, A사 보안 점검 권리

## 5. 개발사가 준비할 것(이게 있어야 A사가 혼자 할 수 있어요)

| 산출물 | 내용 |
|---|---|
| DB 준비 SQL | 소유자·앱 계정, `btree_gist`, 표·시퀀스 GRANT, `ALTER DEFAULT PRIVILEGES`, `access_log`는 INSERT·SELECT·DELETE만. **지금 마이그레이션에 GRANT가 없어서 가장 먼저 필요해요** |
| DB 요구 조건 문서 | PG 17, 풀러 없음(시작 인자 `options`가 거절될 수 있음), `sslmode=verify-full`, NTP, `max_connections` 15 이상, 방화벽 유휴 제한 30초보다 길게, PITR 7일 |
| 온프레미스 설치 안내서 | 환경 값 목록(`tenant.env` 틀 기준), `docker run --read-only --tmpfs /tmp --stop-timeout 50`, 꼭 한 대, 관문·`TRUST_PROXY`, 운영 시작 검사 목록 |
| 이미지 배포 채널 | 판이 박힌 서명 이미지, digest 고정, 사내 레지스트리 복제 방법 |
| 업데이트 절차서 | 백업 → 마이그레이션 잡 → 새 이미지 → smoke → 되돌리기 기준, 릴리스 노트에 마이그레이션·보안 수정 표시 |
| 점검 명령(읽기 전용) | DB 연결·TLS(`pg_stat_ssl`), 서버 버전, `btree_gist`, `schema_migrations` 대 이미지 비교(dry-run), 앱 계정 권한표, `access_log` 줄 수·기간, DB 시계와 앱 시계 차이 |
| 데이터 이전 키트 | 덤프·복원 스크립트, 해시 검증, 비밀 값 인계 절차, 접속기록 인계 확인서, 파기 확인서 양식 |
| 연락표·2차 지원 양식 | 요청 번호·판·시각만 적고 직원 글은 넣지 않아요 |

## 6. 회의에서 찾은 코드 쪽 확인 거리(개발사 판단 필요)

- **접속기록 지우기의 시계 기준이 어긋나요.** 지우기 기준선은 앱 시계로 잡는데(`core/access-record.ts`), 트리거는 DB `now()`로 1년을 검사해요(`010_core.sql`). DB 시계가 앱보다 늦으면 경계에 걸린 줄 때문에 DELETE 전체가 실패해서 `access-log` 보관 단계가 계속 실패할 수 있어요. 10/29 개선 회의는 "DB now()로 자른다"였어요. 사내 DB처럼 시계가 다른 곳에 붙을수록 생길 일이라 고칠 만해요.
- 운영 설정 검사에 DB `sslmode` 확인이 없어요. 빠뜨리면 평문으로 붙을 수 있어요.
- 마이그레이션 GRANT를 별도 스크립트로 두는 일(위 DB 준비 SQL).

## 결론

"개발사 개입 없이 지금 DB를 떼어 내고 A사 사내 PostgreSQL을 붙인다"는 지금 구조에서 현실적으로 안 돼요. DB 주소와 비밀 값은 개발사 계정과 비공개 폴더에만 있고 배포마다 다시 덮어써지며, 기존 자료를 이어 쓰려면 개발사만 가진 `PSEUDONYM_SECRET`이 꼭 필요해요. DB만 옮기는 하이브리드는 개발사가 여전히 모든 자료에 닿아서 보안 이득이 거의 없고 지연·국외 이전·책임 분산만 늘어요. A사가 단독 운영을 원하면 개발사가 한 번 이관해 주는 온프레미스가 현실적인 길이고, 앱 코드는 고칠 필요가 없어요. 대신 그 전에 개발사가 DB 준비 SQL·설치 안내서·점검 명령·이전 키트를 만들어 넘겨야 하고, 이관 뒤에는 접속기록 1년 보관과 업데이트 적용 책임이 A사로 넘어가요.
